# ContextWeave 开发与版本发布规范

**项目：ContextWeave（织境）**  
**适用范围：v0.1 至 v1.0 的所有功能开发、测试、提交和发布**  
**状态：已确认，后续随项目实践维护**

本文档规定每个版本从分析到 GitHub Release 的工作方式。它与 [项目总体规划与技术方案](project-plan.md) 和 [技术栈与长期库选型](technology-stack.md) 一起使用。

仓库根目录的 [AGENTS.md](../AGENTS.md) 是所有设备、对话和协作者开始工作的第一入口；如果它与当前已确认的版本执行文档存在冲突，应先暂停实现并记录冲突。

## 1. 总原则

1. 开发严格按照分阶段版本规划推进，当前只开发 v0.1 至 v1.0 的内容。
2. 每个版本开始前，必须重新分析该版本的目标、依赖、风险、验收方式和不包含的内容。
3. 分析过程中可以提出任何会影响架构、范围、数据、安全、兼容性或发布的确认问题。
4. 在问题得到回答后，必须生成该版本的执行文档。
5. 执行文档需要经过用户二次确认；确认后仍可以多次沟通和维护，直到用户明确满意。
6. 执行文档未确认前，不开始该版本的代码实现，不提前扩大范围。
7. 用户确认的是执行文档的具体版本和修订号；文档发生实质变化时，需要重新确认。
8. 每个版本完成后，必须记录进度、验证结果、已知限制和后续风险。
9. 通过验收后按版本提交到 GitHub 远端，创建 Git tag，并由 GitHub Actions 构建 Windows 和 macOS 产物。
10. 前期不进行代码签名，但发布流程必须保留以后接入签名和公证的配置位置。

## 2. 版本、文档和标签规则

### 2.1 规划版本与发布版本

规划文档使用 `v0.1`、`v0.2` 这种阶段版本；实际 Git 标签使用完整 SemVer：

```text
规划阶段：v0.1
第一次可下载发布：v0.1.0
修复发布：v0.1.1
兼容性增强：v0.1.2
下一阶段：v0.2.0
```

一个阶段可以包含多个开发提交，但只有达到该阶段验收标准后才创建对应的最终 tag。不要为每个临时提交创建公开版本标签。

### 2.2 执行文档

建议目录：

```text
docs/versions/
├── v0.1-execution.md
├── v0.2-execution.md
├── v0.3-execution.md
└── ...
```

每次修改执行文档时保留修订记录：

```text
v0.1-execution-r1：初版分析
v0.1-execution-r2：回答问题后调整内核范围
v0.1-execution-r3：用户确认后的最终版本
```

执行文档至少包含：

- 版本目标和用户价值
- 本版本包含的功能
- 明确不包含的功能
- 用户流程和页面范围
- 数据模型和迁移
- API、IPC、Worker 和内核接口变化
- 依赖和工具链变化
- 浏览器内核和操作系统支持范围
- 测试计划
- 验收标准
- 失败恢复和回滚方案
- 安全、隐私和许可证影响
- 预计提交、tag 和 Release 产物
- 已知限制
- 待用户确认的问题

## 3. 每个版本的标准流程

### 阶段 A：版本分析

开始开发前，先输出当前版本分析：

1. 对照总体路线确认本版本目标。
2. 检查上一版本的已知问题和未完成事项。
3. 拆分功能、数据、界面、IPC、API、Worker、内核和测试任务。
4. 检查是否会影响未来的工作流、团队服务、远程执行或 AI Worker。
5. 确认依赖是否需要新增、升级或替换。
6. 识别跨平台、原生模块、浏览器内核、数据迁移和安全风险。
7. 明确成功标准和不能承诺的能力。

### 阶段 B：问题确认

以下问题可以直接提出，不因为“可能影响进度”而省略：

- 需求是否有多种合理解释。
- 个人模式和团队模式的行为是否不同。
- 是否需要跨设备、跨系统或跨内核兼容。
- 数据是否包含 Cookie、登录会话、代理凭据或其他敏感信息。
- 失败时是否允许重试，重试是否会重复业务写操作。
- 是否需要迁移旧数据或兼容旧版本。
- 是否需要远程执行、队列、WebUI 或 AI 参与。
- 依赖许可证、浏览器内核分发和外部服务条款是否存在影响。
- 用户体验、性能、磁盘、内存或发布体积是否有硬性目标。
- 主题样式，页面布局，内容布局等有关主题的问题
  
问题得到回答后，答案必须写回执行文档，不只保留在对话中。

### 阶段 C：执行文档确认

执行文档必须明确：

- 当前修订号
- 已确认事项
- 未决事项
- 变更后的范围
- 用户验收方式

用户确认前不进入正式实现。用户确认后，执行文档成为该版本的开发基线。

### 阶段 D：实现

实现过程中：

- 按执行文档拆分小任务和逻辑提交。
- 不把临时实验代码直接混入正式模块。
- 新增跨进程数据必须加入 `packages/contracts` 并做运行时校验。
- 新增数据库字段必须有 migration 和回滚说明。
- 新增内核参数必须进入对应 manifest、schema、adapter 和测试。
- 新增依赖必须记录用途、许可证、原生模块和网络行为。
- 如果发现范围、架构或验收标准需要实质变化，暂停该部分实现，更新执行文档并重新确认。

### 阶段 E：验证与验收

代码完成不等于版本完成。必须完成：

1. 自动化检查。
2. 目标平台构建。
3. 关键用户流程手动验收。
4. 异常和恢复流程验证。
5. 产物和校验文件检查。
6. 更新进度、变更记录和已知限制。

### 阶段 F：提交与发布

通过验收后：

1. 合并或提交到主分支。
2. 创建完整 SemVer tag，例如 `v0.1.0`。
3. 推送提交和 tag 到 GitHub。
4. GitHub Actions 从 tag 构建 Windows 和 macOS 产物。
5. 生成 SHA-256 校验文件。
6. 创建 GitHub Release，附上安装包、校验文件、变更说明和已知限制。
7. 在版本进度文档中记录 Release 地址和构建结果。

## 4. Definition of Done

一个版本只有同时满足以下条件，才可以标记为完成：

- 执行文档已确认。
- 版本范围内的功能完成，明确排除项没有混入。
- 关键路径在支持的平台上可以运行。
- 失败、取消、重复启动和异常退出有可解释行为。
- 数据库、IPC、API 和工作流 schema 有版本记录。
- 有意义的自动化测试已通过。
- Windows 和 macOS 构建成功。
- 安装包可以在干净环境中启动或给出明确的系统提示。
- 日志、诊断和敏感数据处理符合规范。
- 依赖、许可证和内核分发来源已经检查。
- Release Notes、已知限制和升级说明已更新。
- 用户完成最终验收。

## 5. 分支、提交和变更控制

### 5.1 分支

推荐保持简单：

```text
main                         # 始终保持可构建
feature/v0.1-xxx             # 短期功能分支
fix/v0.1-xxx                 # 问题修复分支
experiment/forge-v8-vite8    # 独立实验，不进入主发布链路
```

如果单人开发，也建议为风险较高的内核、构建工具或数据库迁移使用短期分支，避免实验污染主分支。

### 5.2 提交

使用 Conventional Commits：

```text
feat(desktop): add environment creation flow
fix(kernel): validate manifest checksum before launch
docs(v0.1): update execution plan
build(release): configure macOS artifact
```

一个提交应表达一个逻辑变化。不要把重构、功能、依赖升级和格式化混在同一个提交中。

### 5.3 变更控制

版本确认后新增需求分为三类：

- 不改变范围且不改变验收：可以记录后直接加入。
- 改变实现但不改变用户行为：更新执行文档的实现部分。
- 改变范围、数据、权限、兼容性或验收：增加执行文档修订号并重新确认。

不能通过“顺手实现”绕过版本范围控制。

## 6. 测试与质量门禁

### 6.1 Pull Request 和普通提交

至少执行：

- TypeScript 类型检查
- ESLint 或 Oxlint
- Prettier/Oxfmt 检查
- Vitest 单元测试
- contracts/schema 校验
- 依赖安装和 native module rebuild 检查

### 6.2 版本发布前

增加：

- 个人模式完整流程
- 团队模式 API 集成测试
- PostgreSQL migration 测试
- MinIO/S3 快照上传下载测试
- 环境租约、心跳、过期和 fencing token 测试
- 浏览器启动、停止、崩溃和锁恢复测试
- 至少两个内核的兼容性测试
- Windows 和 macOS 安装包启动测试
- 低磁盘、断网、服务重启和异常退出测试

### 6.3 质量门禁失败处理

任何门禁失败都必须记录：

- 失败阶段
- 复现步骤
- 是否阻塞发布
- 临时规避方案
- 修复提交
- 是否需要回归测试

不能因为安装包已经生成，就忽略测试失败或把失败标记为成功。

## 7. GitHub Actions 和 Release

### 7.1 CI 工作流

建议至少拆成：

```text
.github/workflows/ci.yml
.github/workflows/build-desktop.yml
.github/workflows/release.yml
```

`ci.yml`：

- 在 Pull Request 和主分支提交触发。
- 安装依赖、类型检查、lint、单元测试和契约测试。
- 可以先不构建完整安装包。

`build-desktop.yml`：

- 在主分支或手动触发。
- 构建 Windows 和 macOS。
- 验证外部 Worker、内核 manifest 和 `extraResources`。

`release.yml`：

- 只在 `v*.*.*` tag 触发。
- 从 tag 对应提交构建，不使用工作区未提交文件。
- 上传安装包、校验文件、SBOM 和 Release Notes。

### 7.2 Windows 和 macOS

首期目标：

- Windows x64；以后再增加 arm64。
- macOS arm64 和 x64；根据 GitHub Runner 和 Electron 支持情况构建。
- 不进行代码签名和公证。
- Release Notes 明确说明系统可能显示未签名警告。
- 安装包名称包含产品版本、操作系统和架构。

不签名不等于忽略完整性校验。每个产物都生成 SHA-256：

```text
ContextWeave-0.1.0-win-x64.exe
ContextWeave-0.1.0-mac-arm64.dmg
SHA256SUMS.txt
```

### 7.3 构建可重复性

- 固定 Node.js 主版本。
- 固定 pnpm 版本和 lockfile。
- 固定 Electron、electron-vite、electron-builder 版本。
- 记录操作系统、架构、Electron 版本和内核版本。
- GitHub Actions 使用固定版本或 commit SHA 的 Action。
- 构建日志记录依赖安装、native module rebuild 和产物哈希。

## 8. 数据库、协议和升级

### 8.1 数据库 migration

- SQLite 和 PostgreSQL 分开管理 migration。
- 每次 schema 变化有正向 migration、回滚说明和测试数据。
- 发布前测试旧版本数据升级到当前版本。
- 不删除用户数据字段，除非有备份、迁移和恢复方案。
- 服务端启动时检查 migration 状态，禁止静默使用错误 schema。

### 8.2 协议版本

以下内容必须有版本字段：

- API `/api/v1`
- IPC 协议
- Kernel Manifest
- Kernel Config Schema
- Workflow Schema
- Profile Snapshot Format
- Worker Message Protocol
- AI Tool Schema

破坏性变化要么增加版本，要么提供迁移函数和兼容窗口。

### 8.3 客户端与服务端兼容

团队客户端和服务端可能不是同时升级。服务端应返回：

- 最低支持客户端版本
- 推荐客户端版本
- API 协议版本
- 内核和快照兼容范围

客户端遇到不兼容时显示升级指引，不应把协议错误伪装成网络错误。

## 9. 浏览器内核和敏感数据规范

- 内核包通过 manifest、HTTPS、SHA-256 和平台/架构校验。
- 内核版本和 Electron 版本独立管理。
- Chrome/Edge 默认只探测用户本机安装，不随项目分发专有二进制。
- 外部浏览器进程使用独立用户目录和 loopback 随机控制端口。
- 浏览器 profile 运行中禁止直接打包；必须停止浏览器并确认锁释放。
- 快照损坏时恢复上一个一致版本，不覆盖当前有效版本。
- Cookie、登录会话、代理密码和模型密钥默认不上传团队服务。
- 用户明确启用敏感数据同步时，使用标准 AEAD 客户端加密和密钥轮换方案。
- 日志、截图、诊断包和错误上报默认脱敏。
- 内核、字体、代理和扩展的许可证单独登记。

## 10. 进度记录

建议目录：

```text
docs/progress/
├── v0.1.md
├── v0.2.md
├── v0.3.md
└── ...
```

每个版本进度记录：

- 当前状态：分析中、待确认、开发中、验证中、已发布、暂停或阻塞。
- 执行文档修订号。
- 已完成任务。
- 进行中任务。
- 未完成任务和原因。
- 测试结果。
- 构建结果。
- Release 和 tag。
- 已知问题。
- 下一版本输入。

进度记录不能只写“已完成”，必须包含可复核证据，例如测试命令、构建产物、日志或截图位置。

## 11. 风险登记

从 v0.1 开始维护风险列表：

- 浏览器内核下载和许可证变化。
- Electron、Node、Vite、原生模块兼容性。
- profile 跨版本、跨系统恢复限制。
- Cookie 和登录会话同步风险。
- 团队租约和旧客户端覆盖。
- 外部网站变化导致自动化失败。
- AI 输出和工具调用风险。
- 第三方依赖漏洞或许可证变化。
- 未签名安装包的系统拦截。

每项风险至少记录可能性、影响、当前措施、责任范围和下一次复查版本。

## 12. 不签名发布的补充约定

当前不进行代码签名和 macOS 公证，但必须：

- 在 Release 页面明确说明未签名。
- 发布 SHA-256 校验值。
- 提供 Windows 和 macOS 的首次启动说明。
- 不在 CI 中配置虚假的签名变量。
- 预留 `CSC_LINK`、Apple notarization 和证书配置的位置，但默认关闭。
- 在 v0.9/v1.0 重新评估签名是否成为发布阻塞条件。

## 13. 本规范的维护

本规范本身也需要版本记录。以下变化需要更新并说明原因：

- 版本确认和用户沟通流程变化。
- 分支、tag 或 CI 发布流程变化。
- Electron、浏览器内核或服务端框架变化。
- 数据迁移、协议兼容或安全要求变化。
- 签名、隐私、许可证和第三方服务政策变化。

在用户没有确认新的流程前，继续使用当前已确认的规范。
## 14. 补充规范（已确认，持续维护）

前面的章节已经定义了版本开发和发布主流程。下面的规则用于减少后期返工、发布争议和数据事故；本节已由用户确认，作为 v0.1 至 v1.0 的正式门禁，并随项目实践维护。

### 14.1 需求追踪和验收证据

- 每个功能必须有唯一的 Issue 或任务编号，并关联执行文档中的功能项。
- 每个功能项写明用户场景、前置条件、成功结果、失败结果和明确排除项。
- 功能项至少能追踪到一个设计说明、一个验证方式和一个版本进度记录。
- 验收不能只写“可以使用”，应记录命令、测试数据、平台、截图或产物位置。
- 需求未形成可验证的验收标准前，不进入“已完成”。

建议在仓库中维护以下关系：

```text
Issue/需求 → 执行文档 → 设计或 ADR → 实现提交 → 测试/验收证据 → Release
```

### 14.2 架构决策记录（ADR）

对会影响后续替换成本的决定单独记录到 `docs/adr/`，例如 Electron 基线、独立浏览器内核、Kernel Adapter、NestJS/Fastify、团队租约、快照格式和工作流协议。每份 ADR 至少包含：背景、候选方案、决定、取舍、影响、迁移或退出条件、状态（提议/已接受/已废弃）。已经发布的协议不能只修改原文，应创建新的 ADR 并说明兼容策略。

### 14.3 支持矩阵和生命周期

- 为客户端、服务端、操作系统、CPU 架构、Electron、Node.js 和浏览器内核维护兼容矩阵。
- 每个阶段明确“开发验证”“构建验证”“正式支持”三种状态，不能把 CI 构建成功当作完整兼容。
- 记录最低支持版本、建议版本、已知不支持组合和停止支持日期。
- API、快照、工作流和内核配置需要定义兼容窗口与弃用提示；删除旧格式前先提供迁移或导出。
- 每次新增内核或平台都必须增加对应的启动、代理、用户目录和恢复测试，而不是只添加一个下拉选项。

### 14.4 安全事件和漏洞处理

- 仓库不得提交密钥、Cookie、代理密码、模型密钥、生产数据库连接串或真实用户数据；示例使用脱敏数据。
- 为依赖漏洞、内核漏洞、会话泄露、权限绕过和数据损坏定义严重级别、响应时限、修复版本和通知方式。
- 影响团队数据的事件必须支持撤销设备、失效租约、轮换密钥、冻结快照和审计追踪。
- 安全修复可以走独立 hotfix 流程，不等待下一阶段功能开发；发布后记录影响范围和升级要求。
- GitHub Actions 使用最小权限，生产发布凭据只放在环境或组织 Secrets 中，不写入工作流文件。

### 14.5 备份、灾难恢复和数据生命周期

- 为本地环境、PostgreSQL、对象存储和工作流定义备份对象、频率、保留期、加密方式以及 RPO/RTO 目标。
- 备份“生成成功”不等于“可恢复”；至少在版本发布前做一次真实恢复演练并记录结果。
- 恢复流程必须支持临时目录校验、哈希校验、原子切换、失败回滚和重复执行。
- 明确定义用户删除、团队解散、设备撤销、快照过期、日志过期和对象存储清理规则。
- 任何会删除或覆盖用户环境的操作都要有二次确认、审计记录和可用的最近版本。

### 14.6 发布通道和紧急修复

- 规划 `nightly`、`preview`（可选）和 `stable` 三种通道；正式 Release 只能来自满足门禁的提交。
- 预发布版本必须在名称、更新说明和安装提示中明确其不稳定性，不能与稳定版本共用不可区分的下载名称。
- 紧急修复使用 `hotfix/vX.Y.Z` 分支和补丁版本号，修复后回合并主分支及正在开发的阶段分支。
- GitHub Release 不覆盖已发布文件；重新构建必须生成新的版本或明确的构建编号。
- 每个 Release 保留源代码、依赖锁文件、SBOM、构建日志摘要、SHA-256 和已知限制。

### 14.7 依赖、许可证和供应链治理

- 新增或升级依赖必须说明用途、版本、许可证、是否包含原生模块、是否执行网络请求以及替换成本。
- 定期检查 npm、GitHub Action、Electron、Node.js 和内核依赖的漏洞与许可证变化；修复优先级写入风险登记。
- 维护第三方依赖清单、NOTICE/归属文件和内核分发记录。不能仅根据 npm 包许可证推断浏览器内核、字体、扩展或补丁可以分发。
- 生产构建使用 lockfile，CI 默认禁止隐式修改 lockfile；依赖更新应有独立提交和回归结果。
- 发布物生成 SBOM，并记录构建所使用的 Node.js、pnpm、Electron、内核和 Action 版本。

### 14.8 测试数据、稳定性和跨平台证据

- 测试数据必须与真实 Cookie、登录会话、代理凭据和订单信息隔离；需要真实平台验证时使用专门的测试账号和最小权限。
- 为关键流程保留可重复的 fixture、mock 服务或 Testcontainers 配置，避免依赖个人电脑状态。
- Flaky test 必须登记、限定重试次数并安排修复；不能用无限重试掩盖回归。
- 跨平台测试记录实际系统版本、CPU 架构、内核版本、代理类型和数据目录位置。
- 浏览器内核的行为差异要在测试报告中区分“适配器问题”“内核能力差异”和“目标网站变化”。

### 14.9 隐私、遥测和支持诊断

- 明确哪些日志、崩溃信息、截图、页面内容和使用统计会被保存或上传；默认不上传网站会话和完整页面内容。
- 遥测或错误上报应默认关闭或取得明确同意，并提供关闭、导出和删除方式。
- 诊断包生成前显示包含的字段，自动脱敏 Authorization、Cookie、代理密码、表单值、页面正文和模型密钥。
- 记录日志保留期限、访问角色和删除方式；生产环境禁止打印完整请求头、页面 HTML 和敏感节点输入。

### 14.10 全球化和可用性基线

面向出海业务和团队使用，从第一版数据模型和界面开始保留：时区、语言、货币、日期格式、地区化数字、键盘操作、清晰的错误信息和基础无障碍语义。业务节点不能把本机时区或字符串格式当作唯一真相，报表和任务结果应保存明确的时区与格式版本。

### 14.11 指纹浏览器和自动化的合规边界

- 每个内核、连接器和业务模板都要记录适用的授权前提、平台条款和数据来源。
- 产品可以支持用户授权下的浏览器隔离、自动化和数据处理，但不把绕过验证码、访问控制、风控或平台限制作为产品承诺。
- 需要登录、提交订单、修改价格、发送消息、删除数据等高影响操作时，必须有明确权限、审计和人工确认策略。
- 新增连接器先做小范围验证和失败保护，不因某个网站当前可用就承诺长期兼容。

### 14.12 工作流和 AI 功能的额外门禁

当工作流、LangChain 或 LangGraph 进入版本范围时，增加以下要求：

- 节点、工具、提示词、模型和输出 schema 均有版本号，并可回放关键输入和输出摘要。
- AI 只能调用 Tool Gateway 注册的最小权限工具；涉及外部写操作时默认生成草稿并等待人工确认。
- 为关键工作流维护固定评测集，验证成功率、误操作、重复执行、超时、成本和权限边界。
- 工作流执行具有取消、重试、幂等键、检查点、死信和人工接管状态；AI 生成的流程不能直接绕过这些状态机。

### 14.13 开源协作和文档维护

- 提供 Issue、Bug Report、Feature Request、Pull Request 和安全报告模板，减少需求信息缺失。
- 每个版本更新 CHANGELOG/Release Notes、升级说明、回滚说明和用户可见的已知限制。
- 重大行为变化、弃用和数据迁移必须在文档中提前说明，并在客户端或服务端显示可理解的提示。
- 本规范、总体规划、技术栈、ADR、执行文档和进度记录发生冲突时，以当前已确认的版本执行文档为准，并在下一次修订中消除冲突。
- 保护 main 分支：禁止强制推送和直接提交，合并前必须通过 CI 和必要的人工审查；紧急修复也要保留可追溯的 Pull Request 或 Release 记录。

## 15. 文档规范和跨设备协作

仓库根目录的 `AGENTS.md` 是所有设备、对话、自动化代理和协作者的第一入口。它记录当前版本闸门、必须读取的文档、文档目录和冲突处理方式。

新建或修改文档时必须：

1. 先读取 `AGENTS.md` 和当前版本执行文档。
2. 选择唯一的权威位置，不为同一主题创建重复的最终文档。
3. 在文件头写明版本或修订号、状态、日期、适用范围和关联文档。
4. 将新文档登记到 `AGENTS.md`、`docs/README.md` 和相关入口文档。
5. 使用 UTF-8 编码，检查链接、控制字符、敏感信息和前后文一致性。
6. 实质变化增加修订号；用户已确认的执行文档发生范围、数据、权限、兼容性或验收变化时重新确认。
7. 被替代文档保留并标记为“已废弃”或“已归档”，链接到替代文档。

文档状态统一使用：`草案`、`分析中`、`待确认`、`生效`、`已废弃`、`已归档`。规划文档提供方向，分析文档记录问题和决策，执行文档作为当前版本的实施基线，进度文档记录事实和证据。同一版本出现冲突时，以用户已确认的执行文档为准；执行文档未确认时，以当前用户最新明确决定和分析文档为准，并暂停代码实现。

新对话或新设备开始工作时，必须按 `AGENTS.md` 中的读取顺序检查当前版本和执行文档修订号。无法确认状态时，只能维护文档，不能修改正式代码、依赖、数据库、构建配置或发布配置。
