## 1. 决策状态与项目定位

### 1.1 如何阅读本规划

| 状态       | 含义                                                       |
| ---------- | ---------------------------------------------------------- |
| 已确认方向 | 维护者已经接受的产品要求与架构边界，是后续开发依据         |
| 当前实现   | 已从仓库静态检查到的实现起点，不等于通过完整验收           |
| 实现约束   | 为兑现已确认方向必须满足的技术与安全条件，具体实现仍需测试 |
| 待验证     | 方案需要原型、攻击面检查或实机证据，不能宣称已经可用       |
| 待决定     | 尚未确定的数值、协议、库或交互细节，不能擅自补成既定承诺   |

“维护者接受设计”“代码已经存在”“质量检查通过”和“产品验收通过”是四种不同状态。本文描述目标及其验收门槛，不提供一份虚构的完成清单。

### 1.2 产品是什么

ContextWeave 是开源桌面浏览器工作台，面向需要管理多个独立浏览器环境、执行授权自动化任务、协作使用环境及开展开发测试的用户。

长期希望循序渐进实现四个方向，而不是四选一：

| 方向               | 产品价值                                       | 当前优先级                                 |
| ------------------ | ---------------------------------------------- | ------------------------------------------ |
| A：多环境管理      | 隔离账号环境，管理身份、代理、扩展和持久化数据 | 先完成可靠的个人使用闭环                   |
| B：浏览器自动化    | 提供程序化控制，并逐步形成可恢复的任务与工作流 | 基础控制入口随个人版首发；进阶能力后续展开 |
| C：AI 网页任务助手 | 在明确授权和可控执行边界内辅助网页任务         | 后续阶段，不成为个人版或团队版的前置依赖   |
| D：开发与测试      | 复用环境与任务能力进行复现、调试和网站测试     | 后续阶段，按真实使用需求拆分交付           |

这不是“先做完所有 A，再做完所有 B”的僵硬顺序。个人版稳定后，下一主要交付目标是团队版；进阶工作流、AI 和网站测试之间的具体先后尚未全部确定。

### 1.3 维护资源与非目标

- 当前及可预见阶段由一位维护者开发，同伴参与真实使用、测试和反馈，没有固定开发团队。
- 按可独立验证的小工作包推进，不以多人并行产能承诺日历排期。
- 项目提供开源软件所需功能，不运营官方托管平台，不提供 ContextWeave SaaS。
- 不以开发、部署或长期维护一个独立的 ContextWeave 业务服务端程序为前提。团队数据库、对象存储和相应运维由用户承担。
- 项目仍需维护数据库 schema、迁移、权限策略、受控数据库操作、客户端适配和部署说明；“不提供服务端程序”不等于免除这些责任。
- 现在和以后都不自研、不长期维护浏览器内核源码或内核分支；使用经过核验的开源上游发行物。
- 不承诺绕过验证码、平台风控或访问控制，不承诺统一的“防关联分数”。自动化和数据处理仅面向用户有权操作的场景。
- 不在首期引入 Web 管理端、分布式调度集群、通用插件商城或完整端到端加密体系。

## 2. 产品形态与工作空间

### 2.1 同一个桌面产品

个人版与团队版是同一个桌面产品中的不同工作空间模式，不是付费等级，也不是两套相互分叉的软件。每个受支持平台发布对应安装包，包内逐步提供相同的工作空间入口。

| 工作空间     | 数据归属与用途                                           | 交付位置                     |
| ------------ | -------------------------------------------------------- | ---------------------------- |
| 本地个人空间 | 用户本机是工作数据的权威来源，默认不依赖服务器           | 个人版首发                   |
| 联网个人空间 | 复用远程工作空间模型，按单成员方式使用用户提供的基础设施 | 后续能力，不是个人版首发门槛 |
| 团队空间     | 用户提供 PostgreSQL 与符合权限要求的 S3；多人按授权访问  | 个人版稳定后的下一主要目标   |

应用支持个人空间以及多个团队空间。不同团队可以连接不同的数据库和对象存储，不假设所有团队共享一个部署实例。

### 2.2 工作空间切换规则

- 环境、代理、成员身份、连接配置、凭据引用、缓存和任务均归属于明确的工作空间。
- 切换空间只改变当前界面上下文，不能把已启动任务或浏览器隐式转移到另一个空间。
- 后台任务固定使用创建时的工作空间身份；后续切换不能改变其授权或结果归属。
- 个人空间数据不得因为加入团队而自动上传；跨空间迁移必须是显式操作。
- 团队连接失败不能把团队数据当成本地个人数据继续写入，也不能自动降级为离线启动。
- 界面应明确显示当前空间、连接状态、访问限制、环境占用和未同步状态。

现有 `TeamSwitcher` 组件可以作为交互起点，但当前侧栏传入空团队列表，仅属于 UI 预留。它不代表成员体系、远程连接、空间隔离或切换事务已经实现，现有字段也不构成收费套餐承诺。

## 4. 个人版首次正式发布

### 4.1 核心使用闭环

目标用户应能够在没有开发者全程指导的情况下完成：

> 创建多个独立账号环境 → 配置身份与网络 → 登录和使用 → 识别并切换环境 → 关闭后重开保留数据及仍有效的登录状态 → 出现问题时从备份恢复。

“保留登录状态”指正确持久化浏览器数据，不保证网站不会主动过期会话、要求二次验证或使迁移后的凭据失效。

### 4.2 首发必须实际可用的范围

| 能力       | 最低交付要求                                                                        |
| ---------- | ----------------------------------------------------------------------------------- |
| 多环境管理 | 创建、编辑、识别、启动、停止和再次打开；环境数据目录隔离；危险操作有确认与恢复提示  |
| 网络与身份 | 每环境代理、语言、时区；代理秘密保护；身份配置可保存、复用并检查实际生效情况        |
| 指纹内核   | 一种正式支持的上游提供方，覆盖约定的三类系统架构；不能以标准浏览器替代指纹能力验收  |
| 扩展       | 支持兼容的 Chrome/Chromium 扩展，允许开发者模式加载未打包或已解压扩展               |
| 数据可靠性 | SQLite 持久化、独立浏览器目录、凭据安全存储、异常退出后可诊断和恢复                 |
| 备份恢复   | 本地、OpenList、S3 三种渠道；手动操作、可选备份包加密、应用运行期间的可配置定时备份 |
| Local API  | 真实可用的本机控制入口，不是空接口或仅规划名称                                      |
| CLI        | 可以实际完成基础环境控制和状态查询，并返回明确的成功、失败和任务结果                |
| MCP        | 可以实际调用受控的基础环境与任务能力，与 GUI/CLI 共享业务边界                       |
| 基础可用性 | 空态、加载、失败、取消、重复操作、日志脱敏和可理解的恢复指引                        |

Local API、CLI、MCP 的首次契约设计应给出一个可验证的最小命令集合，至少形成“发现环境 → 启停环境 → 查询状态或任务结果”的闭环；具体命令名称、授权粒度和传输方式在实现前确定。三个入口都不能只留下未来扩展位置。

### 4.3 不作为个人版首发门槛

- 联网个人空间、自动跨设备同步、SQLite 与 PostgreSQL 的双向合并。
- 团队成员、环境分配、跨设备占用和交接的完整交付。
- 完整可视化工作流、复杂分布式任务、AI 网页助手和完整网站测试平台。
- Chrome 网上应用店直装、集中扩展商城与统一扩展分发。
- 多种正式内核提供方，以及 Windows ARM、Linux 的正式支持。

已有相关代码可以保留，但不能借此扩大首发承诺，也不能以这些后续能力为由删掉已确认的首发功能。

### 4.4 调研采纳：让现有闭环更高效、更可解释

此次按维护者要求比较开源项目后，采纳以下设计方向；具体目标小版本、优先级和验收统一进入[版本台账](version-roadmap.md#31-开源调研增补的执行口径)，不建立第二套排期。

- **轻量功能增量：** 环境单层分组/多标签/备注与保存视图；具名配置模板及仅配置克隆；代理导入预览与一对一分配；可复用的扩展配置集合。复用现有环境、代理、表格、配置修订和任务服务，不重新建设一个管理平台。
- **已有目标细化：** 批量操作先预览范围、执行中可追踪、部分失败可单独重试；身份配置区分稳定属性和网络派生属性；检测区分一致、不一致、未检测、不支持与失败；升级和恢复先展示影响、兼容与冲突。
- **数据保护优先：** 模板默认不带网站会话和秘密正文，新环境具有新的 ID/目录/seed；备份恢复可能保留原身份和会话，必须与克隆区分；扩展代码资源可以复用，每环境可写数据不能被模板或启动修复覆盖。
- **可理解的任务状态：** 最近尝试、最近成功备份和最近恢复验证分别显示；团队的占用、运行、上传与版本提交不合并为一个“已同步”。
- **不提前扩大边界：** 新增轻量能力属于 P1 目标，在对应未来版本线开始前冻结最小范围，不自动追加个人首发硬门槛。既有安全/可靠性要求的 P0 细化仍需验收；第二内核、完整迁移、动作同步和高级网站测试仍先验证或留在远期。

参考项目中没有本项目既定边界的功能，不因有源码就采用：不新增官方托管账号、独立业务服务端、代理/VPN 核心、长期内核分支或自动双向同步。只借鉴设计，不复制未核验许可的代码或把商业 SDK 当作开源浏览器。

## 5. 平台、内核与扩展

### 5.1 首发正式支持矩阵

| 平台                | 架构           | 要求                                                   |
| ------------------- | -------------- | ------------------------------------------------------ |
| Windows             | x64            | 桌面应用、指纹内核、代理、扩展、备份和恢复均需实机验收 |
| macOS Apple Silicon | ARM64 / M 系列 | 同上，另核验平台权限、内核安装及数据兼容性             |
| macOS Intel         | x64            | 同等正式支持要求，不能只验证管理界面能运行             |

最低操作系统版本、发布签名与公证方案尚需确定。Windows ARM、Linux 不在首发正式矩阵内，不代表永久排除。

维护者与测试同伴可以覆盖上述三类设备。CI、模拟环境或某一平台的测试通过不能替代三类设备的完整验收记录。

### 5.2 内核策略

- 首发只正式支持一种内核提供方，降低单人维护成本。
- 优先复用已接入的 `adryfish/fingerprint-chromium`，但具体发行版本、许可、来源、三平台产物与能力必须验证。
- [本次调研](open-source-research.md#33-当前内核与-camoufox能力证据比参数数量重要)确认上游延迟公开补丁：旧版 144 tag 有源码，当前使用的 148 tag 尚未见对应补丁。缺口限定为当前发行版本的源码对应证据，不据主分支目录断言整个项目没有源码。将其作为正式提供方准入的补证项，不把已接入解释为已通过，不擅自切换/降级现有环境或接手源码维护。
- 当前 Adapter 固定的目录版本为 `148.0.7778.215`，内置官方包信息覆盖 Windows x64 和 macOS ARM64，尚未覆盖 macOS x64。这是需要补齐的发布缺口，不是上游所有版本都不支持 Intel Mac 的结论。
- 提供方不足以满足要求时，先核实合格上游发行物，必要时重新评估提供方；不默认接手内核源码，也不无声缩减平台范围。
- 参数可传入、manifest 声明支持或上游 README 提到某能力，都不等于在本项目中实际生效。
- 环境记录身份配置、内核版本和配置格式；升级前检查数据目录兼容性，失败能保留原始数据。
- 不承诺任意字段均可伪装，也不承诺跨内核、跨操作系统保留所有登录状态。

### 5.3 扩展边界

支持开发者模式加载未打包扩展作为可接受的使用方式。应校验扩展目录、权限提示及重启后的有效性，避免将任意本机路径直接暴露给网页或控制接口。

扩展来源、版本、安装状态与其可迁移数据应区分处理。恢复到新设备时可能需要重新选择目录、重新安装或重新授权；不能只保存旧设备的绝对路径就宣称扩展已经完整备份。

## 6. 数据存储总体设计

### 6.1 三类问题分别解决

| 问题         | 目的                                     | 不能混同的概念                           |
| ------------ | ---------------------------------------- | ---------------------------------------- |
| 工作数据存储 | 日常读写、权限与运行状态的权威来源       | 不是把所有数据上传到一个备份目录         |
| 跨设备交接   | 在授权与独占条件下交付最新已提交环境版本 | 不是后台复制正在写入的浏览器目录         |
| 灾难恢复备份 | 在误删、损坏、故障后恢复可信状态         | 日常 S3 快照和版本历史不自动等于独立灾备 |

### 6.2 已确认的存储组合

| 模式或用途   | 结构化数据                                    | 浏览器文件与大对象                        | 凭据与边界                                   |
| ------------ | --------------------------------------------- | ----------------------------------------- | -------------------------------------------- |
| 本地个人空间 | SQLite                                        | 本机独立环境目录                          | 本机秘密使用操作系统安全存储；数据库保存引用 |
| 联网个人空间 | PostgreSQL，复用团队远程模型，单成员          | S3 已提交快照＋本地工作副本               | 用户自行提供基础设施；首期不做双向合并       |
| 团队空间     | PostgreSQL 保存配置、成员权限、占用及版本索引 | S3 保存已提交快照；客户端使用本地工作副本 | 数据库授权与文件授权分别落实                 |
| 备份与恢复   | 统一备份格式中的一致性数据                    | 本地、OpenList 或 S3                      | 三个渠道都可以选择是否加密备份包             |

PostgreSQL 是团队首期唯一正式支持的服务器数据库。具体版本范围、客户端驱动和兼容部署矩阵仍需验证。

### 6.3 必须保持的边界

- 不把 SQLite 数据库放在网络共享目录上充当多人数据库。
- 不把整个浏览器用户目录放进普通数据库字段。
- 团队客户端的本地数据库和文件副本不能取代 PostgreSQL 的授权、占用与已提交版本状态。
- OpenList 首期是备份提供方，不是团队日常交接的主存储。
- S3 备份兼容与团队 S3 主存储兼容是两套不同的验收等级，后者必须满足成员和环境级授权。
- 上传备份不等于自动同步；存在未提交本地修改时，不能因为远端存在旧快照就显示“已同步”。
- 从本地个人模式转到联网个人模式应是显式迁移；不暗中开启 SQLite↔PostgreSQL 双写或冲突合并。
- 不同存储模式复用领域模型与命令，不要求所有数据表、驱动或事务实现完全相同。

## 7. 备份、加密与恢复

### 7.1 用户可见规则

| 项目         | 已确认规则                                                            |
| ------------ | --------------------------------------------------------------------- |
| 渠道         | 本地、OpenList、S3 均支持备份与恢复                                   |
| 备份包加密   | 三种渠道均提供可选开关；关闭时不要求备份加密密码                      |
| 密码         | 开启加密后可自行设置，也可安全随机生成；连接凭据不是备份密码          |
| 远端默认要求 | OpenList、S3 不额外强制用户设置备份包密码；须提示未加密敏感内容的风险 |
| 本地默认开关 | 尚未决定；不把“可选加密”改写为“默认强制加密”                          |
| 定时         | 用户可配置执行时间；仅在应用仍运行且条件满足时调度                    |
| 完全退出     | 停止定时调度，不安装常驻备份服务或系统任务唤醒应用                    |
| 密码恢复     | 项目不托管、不提供官方找回；丢失必要解锁材料可能无法恢复              |

OpenList 的 token、账号密码，以及 S3 的 access key、临时凭据等解决的是连接与访问授权，不等同于备份文件本身的加密。具体采用什么认证方式由已验证的接口决定，不把某参考项目的 token 用法当作所有 OpenList 部署的通用能力。

关闭窗口但应用仍留在托盘或后台，与“应用完全退出”是不同状态，应在界面说明。调度器属于应用进程，不成为独立常驻服务。漏跑任务是否补做、补做上限和保留策略在调度设计中确定。

加密定时备份只有在用户授权安全保存必要解锁材料后才能无人值守运行。操作系统安全存储不可用或需要交互解锁时，应报告失败或等待用户处理，不得静默降级为明文备份。

### 7.2 一致性与备份范围

- 备份包应有格式版本、工作空间与环境标识、配置修订、内核与平台信息、文件清单、大小和校验值。
- SQLite 使用一致性备份机制；不能在数据库运行时随意拷贝主文件并忽略 WAL。
- 浏览器目录只有在确认浏览器及相关任务停止写入后才能捕获可交付快照。
- 定时备份遇到正在运行的环境，首期默认延后该环境，不突然强制关闭用户浏览器；结果需说明哪些环境已备份、哪些仍待处理。
- 排除可重建缓存与明确不需要的临时数据，但要验证排除规则不会破坏会话和扩展数据。
- 凭据、Cookie、登录会话属于敏感内容；导出范围和便携化方案需要单独设计，不能把本机 safeStorage 密文当作跨设备可用的备份。
- 未能备份的秘密或平台绑定数据必须明确列出，并给出恢复时重新录入或重新登录的步骤。
- 具体容器格式、加密库、保留数量、空间上限及敏感字段的默认导出范围尚未定案。

### 7.3 恢复流程

1. 读取并验证包格式、来源信息、解锁结果、文件清单与完整性。
2. 检查目标平台、内核和数据格式兼容性，展示覆盖范围与不能恢复的内容。
3. 确认相关环境停写，将数据解包到受控暂存区，拒绝路径越界和超限内容。
4. 保留原有副本，完成数据库与文件的受控切换；失败可回到恢复前状态。
5. 验证恢复结果，再允许启动；涉及凭据失效或平台绑定时提示重新授权。

不能用“解压完成”代替“恢复成功”，也不能将恢复失败的半成品当作可运行环境。

恢复前形成可确认的计划，区分恢复为新环境、覆盖明确选择的目标和跳过冲突项；名称相同不意味着目标相同。新建恢复需要重映射本地标识和引用，覆盖需要校验目标修订并保留原副本；都不进行浏览器文件/数据库行的智能合并。完成后列出需重新登录、授权或安装的内容，而不是用单一成功提示掩盖部分不可用。

### 7.4 团队备份与灾备

- 团队全量导出、全量恢复和历史清理由管理员控制；普通成员不能通过备份入口绕过环境授权。
- 完整团队备份必须同时覆盖 PostgreSQL 业务关系与所引用的 S3 快照，只导出其中一部分不叫完整灾备。
- 首期允许使用维护窗口暂停相关写入，以取得一致的数据库与对象集合，不追求跨存储不停机备份。
- 日常工作快照、同桶历史版本与独立灾备必须区分，部署说明应说明各自能应对的故障。
- 数据库物理备份、对象存储底层恢复和基础设施可用性由用户运维负责；项目提供应用级格式、验证与恢复指引。

## 8. 团队版的权限与协作行为

### 8.1 访问控制

- 管理员分配环境；普通成员只能访问被授权的环境，包括配置、凭据、文件快照和控制入口。
- 权限是实际数据隔离，不只是隐藏列表、按钮或菜单。
- 每次启动团队环境必须在线校验身份和权限；连接失败或授权被拒绝时，不能凭本地缓存离线启动。
- 普通成员不能共用数据库超级用户、表所有者或 S3 管理员凭据，再由桌面 UI 自行限制。
- 首期以管理员和成员的最小职责划分设计；更细的角色体系在需求成立后再扩展。
- 成员加入、设备接入、凭据轮换和撤销必须在团队交付前形成可执行流程，具体机制仍待权限原型验证。

### 8.2 独占运行、断网与撤权

同一团队环境同时只允许一个运行实例，覆盖不同成员以及同一成员的不同设备。

| 场景                     | 必须发生的行为                                                   |
| ------------------------ | ---------------------------------------------------------------- |
| 正常启动                 | 在线验权，原子取得独占使用资格，获取最新有效版本后运行           |
| 已被占用                 | 拒绝另一实例启动，展示占用状态，不靠 UI 列表缓存判断             |
| 运行中数据库断连         | 提示并重连；宽限期内仍无法恢复则停止相关任务并关闭环境           |
| 已确认权限被撤销         | 立即进入停止任务和关闭环境流程，不等待断网宽限期                 |
| 占用到期但旧实例状态未知 | 进入明确的异常处理流程，不能把租约到期当成旧浏览器已经关闭的证据 |
| 应用崩溃或设备休眠       | 重连、恢复和再次启动前核对进程、占用、授权与本地未提交数据       |

宽限期、续租间隔、租约 TTL、关闭超时和异常接管方式未确定，必须联合验证，不能分别设几个常量就声称满足单实例保证。

这些行为针对受支持、未被篡改的客户端。系统不能保证远程关闭恶意修改后的客户端，不能收回成员已合法取得的明文，也不能替外部网站使登录会话失效。

### 8.3 正常交接流程

1. 在线确认成员与环境授权。
2. 原子申请绑定成员、设备和运行实例的独占使用资格。
3. 拉取并校验最新已提交快照，准备隔离的本地工作副本。
4. 启动浏览器，持续监督进程、权限、连接和占用有效性。
5. 结束使用后关闭浏览器，确认停止写入。
6. 生成新快照并上传新对象，不原地覆盖此前已提交快照。
7. 数据库校验占用、权限和基础版本，条件提交新版本索引。
8. 确认版本提交完成后释放占用；如需放弃修改，走显式的失败或放弃流程。

首期采用完整快照，排除经验证可重建的缓存。增量、去重和流式优化放到取得真实体积、耗时和成本数据之后。

### 8.4 失败不能伪装成成功

| 失败情况                       | 保留与恢复原则                                                     |
| ------------------------------ | ------------------------------------------------------------------ |
| 下载或校验失败                 | 不启动不完整副本，不更改当前有效版本                               |
| 上传失败                       | 保留本地数据和未同步标记；重试或显式放弃，不静默丢弃修改           |
| 上传完成、数据库未提交         | 远端对象仍是未提交对象，不更新有效版本；支持幂等重试与孤立对象清理 |
| 数据库已提交、客户端未收到响应 | 按操作标识查证结果，不能重复生成互相覆盖的提交                     |
| 旧设备或过期占用提交           | 拒绝覆盖新版本，保留可诊断的本地副本并走冲突恢复流程               |
| 撤权发生在运行或上传期间       | 停止受保护操作，不继续以旧授权提交；由管理员决定如何处理遗留修改   |

界面应分别展示连接、权限、运行、占用和同步状态，不能用一个“已同步/未同步”字段掩盖这些不同的事实。

## 9. 无独立业务服务端的可行性与信任边界

### 9.1 固定的产品边界

项目不提供独立 ContextWeave 业务服务端程序；用户提供 PostgreSQL 与 S3。候选实现由桌面受信任进程访问这些基础设施，项目维护数据库侧策略和受控操作。

这不是“数据库放在用户服务器上就天然安全”。厚客户端直连数据库比经过受控应用 API 更难约束；本方案是需要验证的受约束路线，不是已经证明安全的架构。

### 9.2 团队交付前必须完成的验证

| 验证项       | 通过条件                                                                       |
| ------------ | ------------------------------------------------------------------------------ |
| 可信成员身份 | 数据库侧可以确认实际登录主体；不能靠客户端随意填成员 ID 或会话变量冒充别人     |
| 数据库隔离   | 普通成员绕过桌面客户端直接执行 SQL，仍无法读取、修改或控制未授权环境           |
| 文件隔离     | 普通成员绕过客户端直接访问 S3，仍不能读取、列举、覆盖或删除未授权对象          |
| 授权变更     | 数据库与 S3 的授权、撤销和失败补偿有可测试流程，不能出现 UI 撤权但文件长期可读 |
| 版本和占用   | 竞争启动、过期提交、断连、休眠和异常关闭不会静默破坏有效版本                   |
| 凭据生命周期 | 无共享管理员秘密；具备配置、轮换、失效与恢复指引                               |

首次团队发布只支持通过这些测试的 PostgreSQL/S3 部署组合。不承诺任意标注“S3 兼容”的服务都适合作为团队主存储。

若验证失败，应暂停对应团队功能、缩小明确公布的兼容部署范围或重新向维护者提出架构选择。不能用客户端按钮限制代替授权，也不能悄悄恢复旧的自研业务服务端路线。

### 9.3 可信与不可信的对象

- 首期信任用户指定的基础设施管理员，不承诺对数据库或存储管理员隐藏全部业务明文。
- 本地秘密保护、备份包可选加密、传输加密是不同层次，任何一项都不等于完整端到端加密。
- 成员已经解密、复制或导出的数据无法保证远程擦除；授权撤销控制后续访问与正常客户端行为。
- 非法修改客户端、操作系统已被控制、外部网站主动注销等情形不属于客户端可彻底消除的风险。
- 网络连接应限制在用户认可的受控范围，并验证加密连接及证书，不以裸露的公开数据库默认配置交付。

## 10. 分阶段开发、版本线与退出条件

阶段描述产品依赖顺序，具体版本号、逐版本目标和验收只在[版本迭代计划](version-roadmap.md)维护。每条版本线通过自身完成门槛后才进入下一条，不按预定编号机械放行。安全性原型可以提前验证，但不据此扩大个人版首发范围，也不承诺发布日期。

| 阶段                    | 工作重点                                                                             | 退出条件                                                               |
| ----------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| 阶段 0：基线与风险验证  | 复核高风险 BUGS；验证三平台内核来源与能力；做最小 PostgreSQL/S3 授权、占用与快照原型 | 关键路线有证据，阻塞项被明确标记；未通过的团队原型不得被当作可发布能力 |
| 阶段 1：个人版稳定闭环  | 环境与身份、网络、扩展、数据可靠性、三渠道备份、Local API/CLI/MCP、三平台发布验收    | 本文个人版首发矩阵全部通过，测试用户能独立完成核心流程                 |
| 阶段 2：团队版          | 工作空间隔离、部署与接入、成员授权、独占运行、S3 交接、断网撤权、团队灾备            | 权限与并发安全验证通过，故障演练和管理员操作说明齐备                   |
| 阶段 3 及以后：能力扩展 | 联网个人空间、进阶工作流、AI 网页任务、开发测试、必要的性能优化                      | 每项有独立目标与验收；具体先后根据个人与团队用户反馈决定               |

### 10.1 最近的实施顺序

1. 给高风险问题建立复现和回归测试，优先修复凭据、文件路径、事务和启动恢复问题。
2. 核实首发内核在三平台上的可取得性、许可和真实行为，尽早暴露 Intel Mac 缺口。
3. 定义工作空间上下文、稳定标识和命令契约，迁移现有本地数据但不实现不必要的远程同步。
4. 完成个人环境持久化与可靠启停，再建设一致性快照、三渠道备份和可恢复导入。
5. 在同一命令边界上交付 Local API、CLI、MCP，并测试非 GUI 入口的权限和生命周期。
6. 完成个人版三平台验收和恢复演练，再进入团队主要交付。

同时，以最小测试数据提前验证团队身份、数据库权限、S3 文件授权、占用与条件提交。若团队原型暂未通过，可继续交付独立成立的个人版，但必须保持团队版未通过的状态，不让其成为隐性技术债承诺。

### 10.2 团队阶段内部工作包

- 工作空间与配置隔离、管理员初始化和兼容部署说明。
- 数据库主体、环境分配、S3 授权、设备和凭据生命周期。
- 占用、进程监督、断网宽限、撤权、异常接管验证。
- 全量快照发布、版本条件提交、失败恢复与遗留对象清理。
- 团队备份、维护窗口恢复、审计与故障演练。

这些工作包共同构成团队验收，不能把“连接数据库成功”或“TeamSwitcher 能切换名称”单独称作团队版完成。

### 10.3 版本执行台账与完成规则

维护者于 2026-09-26（Asia/Shanghai）授权从 `v0.1.6` 连续逐版开发至 `v1.0.2`，在 `master` 提交、推送、创建 tag 和 Release，取消中途逐版人工确认。质量、许可、数据恢复与平台门槛不变；遇到未决授权或外部阻塞如实报告。具体执行与接续规则见[版本台账第 1.4 节](version-roadmap.md#14-持续开发与发布授权2026-09-26asiashanghai)。

- 从初始基线 `v0.1.1` 进入同线小版本收敛，当前实施状态以版本台账为准；`v0.1.x` 的冻结范围全部验收后才进入 `v0.2.0`；后续版本线同样执行。
- 个人完整能力分解到个人开发版本线，`v1.0.0` 作为重写要求全部通过后的完整交付里程碑。这里的“个人首发”不否认此前 `v0.1.0`、`v0.1.1` 已有发布，也不能用正式编号代替缺失功能。
- 个人稳定后的下一主要目标是团队版；团队接入、权限、独占交接与灾备分别拆为小版本，但所有团队门槛通过前只作为明确标识的实验功能。
- 联网个人、进阶工作流、开发测试和 AI 的远期版本号属于预排，具体优先级尚未冻结。后续调整必须保留已确认的产品边界与首发要求。
- 已有功能优先复用，缺陷修复、功能新增和实机验收分开记录。未完成时追加同线小版本，不把必选范围转成后续愿景。
- 本规划维护“为什么做、做到什么程度”，技术栈维护“技术边界”，版本台账维护“哪个版本做、如何证明完成”，不建立互相冲突的多份版本表。

## 11. 验收与发布门槛

### 11.1 个人版

| 验收领域               | 必须留下的证据                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------- |
| 三平台安装与运行       | Windows x64、macOS ARM64、macOS x64 的设备、系统、应用和内核版本及结果             |
| 环境隔离与持久化       | 多环境数据不串用，关闭重开保持正确身份与仍有效的会话                               |
| 代理、语言、时区、指纹 | 配置输入、有效值检测、错误配置及不支持项的真实反馈                                 |
| 扩展                   | 至少验证受支持安装方式、重启、权限提示和恢复后的处理                               |
| 三种备份渠道           | 手动与定时、加密与不加密、恢复和取消；退出应用后不再调度                           |
| 数据失败路径           | 磁盘不足、断网、错误密码、损坏备份、停写失败、恢复中断、迁移失败                   |
| 三种控制入口           | Local API、CLI、MCP 都能完成同一基础命令闭环，且无法绕过路径、凭据、占用与权限边界 |
| 发布可用性             | 首次使用、日志脱敏、升级兼容、已知限制、许可与安装风险说明                         |

### 11.2 团队版追加验收

- 两个团队的连接、成员、缓存、凭据和任务互不串用。
- 未分配成员通过直接 SQL、S3 请求及本地控制入口都不能访问受保护环境。
- 同一成员两台设备、不同成员同时启动同一环境，只有符合独占规则的实例能运行。
- 网络分区、设备休眠、应用崩溃、租约到期、授权撤销和上传中断均有可复现结果。
- 旧占用不能覆盖已提交新版本；未提交对象不成为默认启动来源。
- PostgreSQL 与 S3 权限变更部分失败时，不以成功提示掩盖残余访问。
- 维护窗口内备份并在隔离目标恢复，核对数据库关系与所有引用对象。
- 管理员能够依照文档部署、升级、轮换凭据、撤权与恢复，无需维护者远程代管。

### 11.3 开源与供应链

开源是已确认的产品目标，但当前仓库根目录尚未提供 LICENSE。正式开源发布前，维护者需明确许可证并补齐文本、第三方许可与再分发说明；本规划不擅自选择具体许可证，也不提供法律结论。

应用、内核二进制、扩展、字体和引用代码分别核验许可。构建通过不等于签名、公证、下载来源或安全审计通过。发布记录必须如实说明签名状态、校验方式、系统要求与已知限制。

## 12. 既有缺陷与迁移管理

### 12.1 `BUGS.md` 的使用方式

报告来自外部模型检查，本次仅完成部分静态核对，尚未逐项复现或完成完整安全审计。按“待复现 → 确认 → 修复 → 回归验证”的流程处理，不直接把整份报告复制成已证实缺陷清单。

优先工作包：

| 工作包               | 现有证据与下一步                                                                                  |
| -------------------- | ------------------------------------------------------------------------------------------------- |
| 凭据与文件路径       | 静态检查发现代理测试可组合传入目标与已存秘密、Worker 任务标识参与路径拼接；需复现越界行为并补回归 |
| 保存原子性           | 代理与关联环境更新需整体事务；凭据文件与数据库不共享事务时还需补偿策略                            |
| 启动与窗口恢复       | 主窗口销毁引用、数据库初始化失败的用户可见恢复入口需复核与修复                                    |
| schema 与迁移        | 对照真实 DDL、Drizzle schema 和 repository，不能以存在 ORM 依赖证明一致                           |
| 测试、CI、打包和发布 | 重新以当前提交与产物核验覆盖缺口，不沿用旧产物测量值                                              |

报告中的部分表述需要重新界定：CDP 控制命令超时不等于“网页 HTTP 响应超过五秒”；生产页面仅存在 meta CSP 不能单独证明漏洞；旧 alpha 安装包的体积不能直接套用当前产物；“违反旧规划”也不能单独证明新产品路线中的缺陷。

本次只重写规划，不修改、删除或宣称修复 `BUGS.md` 中的问题。

### 12.2 渐进迁移而不是无证据重写

- 先确认现有行为与数据，再改变 contracts、存储与运行边界。
- 将旧的本地数据纳入个人工作空间时，保留环境标识、目录、代理关联与凭据引用，提供迁移前备份和失败恢复路径。
- 数据库 migration、文件迁移、秘密重加密与内核数据目录升级是不同操作，分别记录版本和回退条件。
- 不以删除本地数据、自动重建空库或隐式改用另一个内核来掩盖失败。
- 现有日志、主题、更新和列表功能可以保留；旧文档中的精确样式、刷新间隔和历史完成描述不自动上升为不可变产品要求。
- 本轮不修改 README 中已有的用户改动；其中旧版本路线摘要以及桌面包 README 的旧范围说明需在后续保留原意的前提下同步，不作为本规划的范围依据。

## 14. 本次重写替换了什么

1. 用“个人稳定 → 团队 → 后续扩展”的交付顺序替换旧路线，基础 Local API/CLI/MCP 纳入个人首发；后续按维护者要求在版本台账中细分为有完成门槛的版本线和小版本。
2. 明确同一应用的个人与多团队工作空间，不把团队版设计为收费套餐或另一套产品。
3. 用用户提供 PostgreSQL/S3、项目维护客户端与数据库策略的边界，替换以自研独立团队业务服务端为前提的旧方案。
4. 明确本地个人 SQLite、远程个人复用团队模型、团队 PostgreSQL＋S3＋本地副本，禁止将备份、同步和工作存储混为一谈。
5. 把本地、OpenList、S3 统一纳入可选加密与应用内定时备份，排除完全退出后的常驻调度。
6. 将 Windows x64、两种 Mac 架构列为首发正式目标，并明确不承担内核源码维护。
7. 将旧文档中的完成声明、UI 精确约束和候选依赖清单，改为可复用实现、待验证目标或待决定事项。
8. 将权限、撤销、独占运行、失败交接和恢复列为团队硬性验收门槛，而不是日后补充的优化项。
