# Simprint v0.2.32 工作流审阅与产品规划

研究日期：2026-09-20。  
项目：ContextWeave（织境）

本次核对 GitHub 最新 Release v0.2.32，并克隆其源码进行静态追踪。Release 与 main 均指向 d2dc939bfae8efda8e4e4d791587d7a364ca4dd8。检查范围包括节点目录、属性面板、画布与工作流转换、变量、编辑器试运行、正式执行、CDP 适配器、本地脚本桥接、任务存储与业务分发。未安装运行发布二进制，未连接真实电商账号；以下“实现”指存在对应源码路径，不表示已经验证所有网站兼容性，也不是对整个项目的完整审计。

用户已经试用最新 Release，认可节点设置和交互。我们的目标是独立开发开源桌面产品，经 GitHub Releases 分发，团队服务由使用者自建，支持成员接力使用同一登录环境，并逐步覆盖工作流、测试、电商运营、出海业务和数据采集。

当前项目的最终客户端基线已确定为 Electron + React/TypeScript；Tauri/Wails 仅作为备选。Electron 只负责管理界面和本地协调，实际网站访问由独立浏览器内核进程完成。最新总体方案以 [项目总体规划与技术方案](project-plan.md) 为准。

## 一、结论

Simprint 最值得学习的是“可配置节点 + 可视化流程 + 运行中点选目标 + 即时结果预览 + 环境绑定”。这个交互方向适合运营用户，应作为我们第一版的重要参考。

需要重点扩展的是数据处理能力和执行可靠性。单个浏览器操作可行，并不等同于批量采集、无人值守执行、团队接力和业务修改已经可靠。我们应保留交互思路，独立设计持久化执行器、结构化数据、业务结果校验与跨设备协调。

其工作流不是全部用 Rust 实现：画布使用 React Flow，流程执行器是 TypeScript，浏览器操作主要走自实现 CDP 适配器，本地 JavaScript 则由 Rust 启动系统 node。因此，“需要工作流就必须选 Electron”不成立；Tauri 同样可实现这类体验。Electron 的优势应限定为 Node.js 工具整合、渲染一致性及工具链统一，不能当作工作流能力的独占优势。

## 二、14 类节点及其实际配置

来源：[S1] 节点目录、[S2] 属性面板、[S3] 执行器、[S4] 浏览器适配器。

| 节点 | 可配置或交互内容 | 源码中的执行路径与边界 |
|---|---|---|
| 点击元素 | CSS/XPath、单击/双击/右键、等待元素、运行中捕获目标 | 基础点击有实现；当前执行器没有把点击方式和等待开关传给适配器，最终调用 DOM element.click() |
| 输入文本 | 目标、文本、清空、慢速输入 | 基础填充有实现；当前适配器直接设置值并发出 input/change 事件，未落实清空开关及慢速输入语义 |
| 打开新页面 | URL、等待加载 | 创建新标签页并导航；有加载事件等待 |
| 选择标签页 | 标签页位置 | 通过本地内核接口取得目标并附加 CDP 会话；依赖 Simprint 接口，不能原样接到任意浏览器 |
| 关闭标签页 | 标签页位置 | 通过本地内核接口关闭并切换目标 |
| 截图 | 视口、整页、指定元素 | 有截图路径，编辑器把结果回填为预览 |
| 滚动页面 | 到元素、按视口、到页面顶部或底部 | 有对应实现 |
| 等待 | 时间或元素 | 有定时等待和元素轮询；需要另外设计统一取消机制 |
| 条件判断 | 元素可见、文本出现、URL 包含 | 有 true/false 分支；不等同于独立测试断言体系 |
| 循环 | 次数、容器内子节点 | 当前为计数循环，有循环体遍历；未提供一等的逐条数据遍历节点 |
| 退出循环 | 放置于循环区域内 | 有跳出路径及部分结构检查 |
| 提取页面数据 | 文本、链接、输入值、输出变量、结果预览 | 默认定位一个元素并返回字符串；列表和表格结构化提取需要新增能力或自行写脚本 |
| 上传文件 | 本地文件选择、运行中点选上传目标 | 使用 DOM.setFileInputFiles；配置保存的是本机路径，跨设备运行需要资源映射 |
| 执行脚本 | 浏览器/本地模式、脚本、输出变量、结果预览 | 浏览器模式通过 Runtime.evaluate；本地模式通过 Tauri 调用 Rust，再执行系统 node |

变量支持 {{变量}} 插值、对象属性和数组索引访问，以及对部分 JSON 字符串的解析。任务变量支持运行前填写。浏览器脚本和本地脚本均可产生输出，因此高级用户可以扩展流程，但不能据此宣称已经有易用的 HTTP、表格、数据库等独立节点。

## 三、值得沿用的交互

### 1. 运行中点选目标

当节点缺少目标时，执行器进入 awaiting_input，安装浏览器点选逻辑，用户悬停时可见高亮，点击后记录 XPath 和元素摘要，再继续执行。编辑器回调把选择器写入节点。[S3][S4][S5]

价值：用户不必先学 CSS/XPath，创建工作流的过程接近实际操作。

我们的改进：明确区分“配置/试运行”和“正式运行”。正式无人值守任务应预检目标是否完整；运行途中目标失效时记录问题并请求接管，而不是默认等待一个无人可见的点选动作。点选目标与执行真实写操作也应在交互上清楚区分。

### 2. 即时输出预览

提取、脚本和截图会通过回调更新节点预览。这有助于用户发现选错元素、提取到空内容、变量名称错误。[S5]

我们的改进：结果面板展示类型、字段、样例行、行数、来源及错误。不能把所有输出都压成文本；表格、文件、JSON 对象和金额应有明确类型。

### 3. 循环区域与条件连线

把重复步骤放进循环区域、把 true/false 显示成不同分支，适合表达翻页和异常判断。

我们的改进：循环体入口应在流程数据中显式指定，不让画布坐标参与业务执行语义。Simprint 当前在多个无入边子节点中按画布位置选择入口，说明需要将布局与执行结构进一步分离。[S3]

### 4. 可搬运工作流

导入导出有 schema_version；便携导出清空环境 UUID，便于在另一处重新绑定环境。[S6]

我们的改进：导出包显式列出必需环境、凭据引用、输入文件、节点版本和平台连接器。导入时做映射与缺失检查；只清空环境 ID 并不能解决本地文件路径和敏感配置的可移植性。

## 四、源码追踪发现的能力边界

以下用于指导我们的设计，不能扩大为对所有版本或所有执行方式的否定。

### A. 部分节点配置尚未完整落到执行

点击面板有 double/right，工作流转换会保存 click_type，但 RpaRunner 只调用 adapter.click(target)，适配器用 element.click()。输入面板的 clearFirst/typeSlowly 也未传入当前填充实现。[S2][S3][S4]

影响：运营用户看到的选项应与运行结果一一对应。我们应以同一个节点定义描述配置、输入输出、默认值及执行能力，并为有行为差异的选项做契约测试。

### B. 策略字段不等于调度引擎

任务模型和设置面板有计划、重试、超时；schema 还包含串行/并行及并发度。当前正式执行 hook 使用 for...of 逐个环境 await 执行，未消费并发、重试和全流程超时配置。对相关源码路径的检索未找到这些字段对应的完整调度执行链路。[S7][S8]

节点级等待超时和本地脚本 60 秒超时确实存在，不能误写为“没有任何超时”。目前缺少的是统一的任务级机制及配置闭环。

我们的设计应有独立任务状态机、分级超时、取消信号、节点级重试、资源配额和调度服务。定时任务还需明确时区、夏令时、错过计划后的补跑策略和设备离线状态。

### C. 正式执行主要由前端组织

RpaRunner 在前端 TypeScript 中执行，状态通过 React hook 更新。数据库里存在 rpa_task_runs 表和写入函数，但此次检索没有找到当前正式执行 hook 调用这些写入函数的完整链路；该 hook 主要订阅步骤状态，没有像编辑器那样完整接入截图及数据输出回调。[S5][S7][S9]

这不能当作持久化、可断点恢复的后台执行服务。我们应把执行从页面生命周期中移出，先持久化运行记录，再发布状态事件给 UI。真正恢复时要判断已发生的业务操作，不能仅按“最后一个节点”盲目续跑。

### D. 数据与元素定位仍较基础

提取采用 querySelector 或 XPath 的首个匹配结果。目标捕获保存主 XPath 和元素摘要，目前 candidates 仅包含该主 XPath；未见候选重试、语义定位或完整 iframe/Shadow DOM 定位链路。[S4]

电商后台常有动态表格、弹窗、异步刷新和重复按钮。我们需要定位范围、匹配数量、可见性、遮挡检查、框架内目标及稳定属性，并将“找不到”和“找到多个”作为不同错误。不能自动在多个订单按钮中猜一个点击。

### E. 本地脚本依赖用户机器上的 Node.js

Rust 检查 node --version，生成临时 .cjs 文件，并调用 Command::new("node")。脚本可接收 vars、require 和 fetch。[S10]

若面向普通运营用户，应提供受管理、固定版本的执行运行时，而不是要求用户自行配置 Node.js。脚本执行权限、超时后的进程清理、日志输出和依赖安装也应有明确设计。本地脚本并不天然沿用浏览器代理，业务出口需要单独定义。

### F. “团队页面”不等于跨设备交接

v0.2.32 Release 明确移除旧独立服务端。http_post 当前直接分发到内嵌业务数据库，未知路由本地失败。[S11][S12]

我们的“服务由用户自建、两名成员接力同一环境”需要独立实现服务器身份认证、授权、设备管理、运行租约、快照版本与提交校验，不能从页面存在团队栏目推断这些已经具备。

## 五、将需求映射到真实业务

以下是拟议场景，不是声称 Simprint 已经内置对应平台功能。具体平台通过官方 API 或页面操作实现，需要分别验证权限与能力。

| 场景 | 用户输入 | 核心流程 | 可交付结果 | 当前基础之外需要补充 |
|---|---|---|---|---|
| 商品与价格巡检 | 店铺/站点、SKU 或 URL 表、规则 | 获取商品数据、解析币种与金额、比较规则、保留证据 | 异常商品表、变化记录、截图 | 表格输入、逐行循环、金额类型、历史比较、断言 |
| 订单/库存报表整理 | 店铺、日期、报表类型 | 请求导出、等待下载、解析文件、去重、合并 | 标准化报表及来源记录 | 下载完成事件、文件产物、CSV/XLSX、字段映射、校验 |
| 商品资料维护 | SKU、图片、描述、价格草稿 | 校验输入、上传资料、预览变更、提交、回读确认 | 逐条操作结果与失败原因 | 素材资源、业务键、人工审核节点、幂等和结果验证 |
| 出海落地页检查 | 地区、语言、页面列表 | 打开页面、检查链接/表单/货币/文案、截图 | 按地区的检查报告 | 环境矩阵、HTTP 状态、断言、截图比较、地域来源记录 |
| 数据采集 | 列表入口、字段定义、更新规则 | 翻页/滚动、批量提取、清洗、去重、增量保存 | 数据集、失败项、采集时间与来源 | 列表提取、分页策略、游标、去重键、重试队列、数据出口 |
| 网站功能回归 | 测试环境、数据、预期结果 | 页面/API 操作、断言、收集失败证据 | 用例结果、截图、日志与历史趋势 | 测试套件、夹具、断言、清理步骤、标准浏览器对照 |
| 内容与运营报表 | 已授权渠道、日期、素材或规则 | 读取指标/生成草稿、校验、必要时人工确认 | 运营汇总、草稿或发布记录 | 渠道连接器、内容资源、凭据作用域、人工任务 |

出海业务还需区分：任务运行时区、店铺业务时区、报表时区、浏览器时区。金额保存数值与币种，保留原始文本，避免把不同地区的小数和千分位格式混淆。平台账号、店铺、浏览器环境也应为不同对象：一个账号可能管理多个店铺，连接器授权也不总是依赖浏览器登录。

## 六、建议的节点体系

### 通用浏览器节点

打开/复用页面、选择标签、点击、输入、下拉框、键盘、悬停、滚动、上传、下载、截图、等待；支持目标点选和必要的 iframe/Shadow DOM 路径。优先验证常用节点的稳定性，再增加低频动作。

### 数据节点

读取表格、HTTP 请求、解析 JSON、提取列表/表格、字段映射、过滤、排序、去重、合并、金额/日期转换、写出文件、写入数据集。运行产物采用文件引用与数据集引用，避免大文件或大表一直装进前端状态。

### 流程节点

条件、按数据项循环、计数循环、分页循环、限速、错误分支、子流程、人工处理、结束。并行是受资源约束的调度能力，不只是多画几根连线；同一个浏览器环境内的页面操作默认串行，不同环境可限额并行。

### 测试节点

元素、文本、URL、HTTP 状态、数据字段、金额范围、数量和截图的断言。条件分支用于控制下一步，断言用于记录预期与实际并形成报告，两者应明确区分。

### 业务连接器与模板

先为一个平台提供少量高价值动作，其他平台通过连接器扩展。官方 API 适用时优先使用 API；浏览器负责页面独有操作。连接器应处理授权、分页、限流、字段变化及错误映射，不要求运营用户自己拼 API。

### 专家扩展

保留浏览器脚本、本地脚本和外部程序接口。AI 可辅助生成草稿、映射字段、解释失败，但涉及真实修改的执行计划需要清楚可见，并记录实际动作；不依赖 AI 在正式执行中悄悄猜测目标。

## 七、保留 Simprint 交互，再补三块产品界面

1. 数据与变量面板：区分输入、当前循环项、节点输出、环境信息、密钥引用；显示类型和样例。
2. 运行检查面板：显示步骤、目标匹配、输入输出、截图、失败原因、重试记录和人工待办。
3. 资源绑定面板：选择工作空间、店铺、环境、凭据、数据集、文件和执行设备。

一般用户通过业务模板填写店铺、日期、文件和规则即可运行；高级用户可以展开底层流程并修改节点。模板应引用同一执行引擎，避免维护“简单模式”和“高级模式”两套执行逻辑。

编辑器的下一步不是无限增加节点数量，而是让每个节点具备：输入、配置、输出、运行状态、错误语义、超时、取消、权限和版本。先在代码里形成统一节点定义，等多个真实场景证明扩展方式后再做第三方插件市场。

## 八、团队接力与运行恢复

人工与自动化使用同一套环境占用机制。工作流也应作为一个持有租约的使用者，而不能在成员打开环境时另起任务。

建议状态分为两组：业务执行状态与环境同步状态。例如“订单报表已下载，环境上传失败”不能等同于“订单任务失败，应全部重做”。

租约由服务器协调，上传提交携带环境版本和租约代次，拒绝旧客户端覆盖。网络分区时，服务器无法凭租约到期让旧浏览器瞬间停止；客户端需要失联策略，重新接管时还要明确旧设备状态。这是协议设计问题，换桌面框架不会解决。

跨设备恢复还依赖浏览器版本、操作系统密钥及网站自身验证。首版应限定经过验证的系统/内核组合。接管记录不能代替网站会话迁移实测。

写操作的重试策略应以业务键和结果查询为基础。例如修改某 SKU 价格后客户端断线，恢复时先查询当前价格，再决定是否重试。不能承诺用一个通用工作流引擎就实现所有平台的“恰好执行一次”。

## 九、对技术选型的修正

确定性最高的部分是 React + TypeScript + React Flow 编辑器、版本化工作流定义、独立执行器、浏览器适配器、自托管协调服务。

Electron + TypeScript 仍是减少 Node.js 工具整合成本的合理基线，但不能以“有工作流”排除 Tauri。Simprint 已证明 Tauri + TypeScript 工作流 + Rust 本地桥接是可行架构，其本地脚本也实际使用 Node.js。

Tauri + Rust 本地宿主 + 独立 TypeScript/Node.js 执行器同样符合目标。代价是多语言边界和附带运行时发布；收益主要是较小的管理端开销和明确的本地能力边界。Wails + Go + 同一独立执行器也能满足功能。

关键改进是执行器不依赖 React 组件生命周期、不直接依赖桌面框架、不把任务状态只存在内存。正式框架选择应验证打包后运行、环境启动与清理、任务取消、长时日志、断网恢复及真实资源占用。客户端框架、Node.js 版本、浏览器内核版本和工作流版本分别管理。

## 十、实施顺序与验收

第一阶段：复现一条完整的交互链路。建立独立环境、节点点选、输入/点击/提取、变量、条件、循环、试运行结果；固定节点配置与执行语义，不先堆大量开关。

第二阶段：用“商品巡检”和“订单报表整理”检验实用性。补表格、列表提取、下载、数据转换、断言、结果产物和失败项重跑。再用一个标准浏览器的登录/购物车测试验证测试模式。

第三阶段：引入用户自建服务、任务队列、设备心跳、环境租约、快照提交和持久化运行记录，完成两台电脑的环境交接。第一阶段就预留 ID、版本和事件模型，但不提前拆分微服务。

第四阶段：扩展电商平台连接器、子流程、人工处理、可复用模板和无人值守执行节点。

验收应覆盖：

- 同一个节点所有可选行为确实生效，界面没有“保存了但执行忽略”的配置。
- 页面布局变化、重复目标、慢加载、空结果均有可理解的反馈。
- 大表按批次处理；分页重复、最后一页和增量重跑不造成重复数据。
- 取消可以中止等待、网络请求和受管理的脚本进程，状态可解释。
- 同一环境不会被正常在线的人工与自动化同时占用，过期提交被拒绝。
- 业务操作已完成而同步失败时，不重复执行写操作。
- 多店铺金额、时区、报表日期保留来源并转换正确。
- 真实安装包可运行，普通用户不需要手动准备脚本运行时。
