# ContextWeave 技术栈与长期库选型

**重写日期：** 2026-09-24

**对应路线：** [项目总体规划与技术方案](project-plan.md)；逐版本工作归属及源码证据见[版本迭代计划与功能基线](version-roadmap.md)。

**文档职责：** 将已确认的产品边界转化为技术职责、数据模型、实现约束、验证门槛和库选型规则。工程协作要求仍见 [AGENTS.md](../AGENTS.md)。

本文不是依赖安装清单，也不表示下面的目标架构已经实现。既有代码事实、已确认的技术方向和待验证的实现方案分别标注；版本以仓库锁文件及实际验收组合为准，不在规划中长期宣称某个库或内核是“最新”。

技术能力只有在对应版本线的验收通过后才可标记完成。版本台账按 `v0.1.1` 源码基线区分已有实现与差距；本文件不重复维护另一套小版本表，也不因版本号递增而降低安全、数据一致性或三平台要求。

## 1. 技术决策分层

### 1.1 已确认的架构方向

| 领域         | 基线                                                     | 排除或延期的路线                                       |
| ------------ | -------------------------------------------------------- | ------------------------------------------------------ |
| 产品形态     | 同一个桌面应用中的本地个人、联网个人与多个团队工作空间   | 两套互相分叉的个人/团队产品、官方 SaaS                 |
| 本地个人数据 | SQLite＋独立浏览器目录＋操作系统安全存储                 | 网络共享 SQLite、默认要求远程服务器                    |
| 远程工作空间 | PostgreSQL 结构化数据＋S3 已提交快照＋本地工作副本       | 将完整浏览器目录存入数据库、首期多数据库支持           |
| 联网个人     | 复用单成员远程工作空间                                   | 首期 SQLite↔PostgreSQL 双向合并                        |
| 项目交付边界 | 客户端、schema、迁移、数据库授权逻辑、存储适配及部署说明 | 独立 ContextWeave 业务服务端程序                       |
| 备份         | 本地/OpenList/S3 统一逻辑格式、可选加密、应用内定时调度  | 用 OpenList 承担首期团队交接主存储、退出后常驻备份服务 |
| 浏览器内核   | 一个优先验证的开源上游提供方，兼容三类目标平台           | 自研或长期维护内核源码/分支                            |
| 控制入口     | GUI、Local API、CLI、MCP 共享受控命令                    | 个人首发仅预留接口、未经确认的公网控制服务             |

桌面受信任进程直连 PostgreSQL/S3 是为满足上述边界需要验证的候选实现，并非已经证明安全。是否能在普通客户端可绕过的条件下兑现权限与版本约束，是团队交付的前置门槛。

### 1.2 当前可复用的实现基线

| 当前仓库内容                              | 采用方式                     | 必须注意                                                       |
| ----------------------------------------- | ---------------------------- | -------------------------------------------------------------- |
| TypeScript、pnpm workspace                | 继续作为语言和包管理基础     | 开发 Node 与 Electron 内置 Node 分别验证                       |
| Electron、electron-vite、electron-builder | 复用进程、构建与安装包基础   | 构建成功不等于三平台发布验收通过                               |
| React、Tailwind、Base UI/shadcn、现有组件 | 复用已有界面与交互基础       | 本轮没有把旧主题、布局和每个组件实现重新确认为不可变要求       |
| TanStack Router/Query/Table               | 分别承载路由、异步数据及表格 | 按空间隔离缓存；运行任务不依赖页面挂载                         |
| React Hook Form、Zod、contracts           | 复用表单与跨边界校验         | 校验参数形状不等于完成业务授权                                 |
| `node:sqlite` 的 `DatabaseSync`           | 当前真实本地数据库驱动       | 同步 I/O 的阻塞影响需测量，不能误称已全部异步化                |
| Drizzle 依赖与 schema 文件                | 作为现有代码复核             | 不能据此声称 repository 已完全使用 ORM，或迁移与 schema 已一致 |
| safeStorage 凭据封装                      | 作为本机秘密保护基础         | 加密后存本机文件不等于逐条写入系统凭据库，也不保证跨设备解密   |
| kernel-core、fingerprint/standard Adapter | 保留边界，逐项验证能力       | Adapter 存在不代表该提供方进入正式支持矩阵                     |
| Playwright Core、CDP 与 Worker 基础       | 按任务需求复用               | 避免多个控制器无协调地修改同一个浏览器会话                     |
| 日志、更新、代理与归档相关现有依赖        | 核对用途后保留或替换         | 已安装不等于新备份或团队能力已经完成                           |

当前 storage 显式启用 WAL 和外键，Main 使用一个 `contextweave.sqlite` 与环境目录。这是迁移起点，而不是最终工作空间隔离方案。

### 1.3 待选而非默认安装的组件

PostgreSQL 客户端驱动、远程 schema 工具、S3 SDK、OpenList 传输实现、备份归档与密码派生库、Local API 传输库及 MCP SDK 的具体组合，在相应验证工作包中确定。

不因旧文档列过 Fastify、Redis、BullMQ、OIDC、React Flow 或 AI/RAG 库，就将其视为本轮必装依赖。现有依赖的清理同样应依据真实用途，而不是为缩小列表进行无证据删除。

## 2. 应用进程与命令边界

### 2.1 目标调用方向

```text
Renderer / GUI
    │ 类型化 Preload API
    ▼
应用命令层 ◀── 本机 Local API / CLI / MCP 入口
    │ 身份、工作空间、参数、权限、幂等与任务归属检查
    ├── 本地 repository ── SQLite
    ├── 远程 repository ── PostgreSQL 的受控权限与事务
    ├── 凭据服务 ── 操作系统安全存储支持的秘密保护
    ├── 浏览器运行服务 ── 独立内核进程与环境目录
    └── 任务/快照/备份服务 ── 受限 Worker ── 本地文件 / OpenList / S3
```

这是职责图，不要求一次新增同名 package 或把所有工作都堆进 Main。首先在现有边界内实现清晰接口，只有稳定的复用需要才拆包。

### 2.2 职责约束

- **Renderer：** 页面、表单和短生命周期交互状态；不直接访问数据库、文件系统、远端存储、任意 IPC 或调试端口。
- **Preload：** 暴露最小白名单 API，不传出 Electron/Node 完整对象；请求与响应均有运行时契约。
- **Main 与领域服务：** 可信上下文解析、授权、路径解析、凭据使用、窗口和任务协调；不保存 React 页面状态。
- **Worker：** 接收受限任务输入，处理下载、归档、校验等长任务；有进度、取消、超时和结果协议，不拥有任意目录、管理员数据库账号或任意 shell 权限。
- **浏览器进程：** 访问实际网站，使用独立用户目录，不与管理界面共享本地能力。
- **远程存储：** PostgreSQL 与 S3 各自执行真实授权，不能因客户端已检查就取消基础设施侧限制。

工作空间、身份、环境和命令参数应由服务层重新核验。Renderer、CLI、MCP 发来的 ID、文件名或成员声明都是待验证输入。

### 2.3 状态与任务

界面筛选、远程查询缓存、持久化配置、运行状态、占用状态、备份任务和同步状态分别管理。不能用一个全局 store 或单个 `status` 字段替代它们。

长任务拥有稳定任务 ID、工作空间归属、发起主体、进度、取消请求、错误码和最终结果。页面切换或退出某个路由不取消后台业务；取消必须清理临时资源并保留已提交事实。批量操作报告部分成功与部分失败，不能只返回一个总成功提示。

## 3. 工作空间与核心数据模型

### 3.1 必要的逻辑实体

以下是目标职责，不是已确定的全部 SQL 表或 TypeScript 类型名称。

| 实体                       | 关键职责                                                     |
| -------------------------- | ------------------------------------------------------------ |
| Workspace                  | 本地/远程模式、稳定标识、存储连接引用与隔离范围              |
| Member / Device            | 团队主体、设备和可信数据库身份映射；设备标识本身不是认证凭据 |
| Environment                | 身份、代理、内核、扩展引用、配置修订及工作空间归属           |
| CredentialReference        | 指向受控秘密，不在普通环境记录或日志中内嵌秘密               |
| EnvironmentGrant           | 成员对环境及相应操作的授权                                   |
| RuntimeSession             | 一次实际浏览器运行及所属设备、进程身份和终止结果             |
| EnvironmentLease           | 团队独占使用资格、持有者、期限与递增代次                     |
| SnapshotVersion            | 基础版本、快照对象引用、哈希、大小、格式与提交状态           |
| LocalWorkingCopy           | 本机副本的基础版本、本地修改、上传及提交状态                 |
| Task / AuditEvent          | 任务幂等与结果、必要的脱敏操作记录                           |
| BackupJob / BackupManifest | 调度规则、捕获范围、文件清单、格式、校验与恢复元信息         |

### 3.2 隔离与命名

- 命令上下文至少能确定 `workspaceId`、可信主体、目标资源及操作标识；成员身份不能仅来自客户端参数。
- 本地个人 SQLite 是本地业务的权威来源；远程工作空间的本地数据库只是连接配置、缓存与操作日志，不能代替远端授权或提交记录。
- 个人数据、各团队缓存、工作目录、备份配置及凭据引用按空间分隔。物理上采用每空间文件还是严格分区表，在迁移设计中确定并测试。
- Query 缓存键、下载缓存引用和任务订阅都应包含空间上下文，切换空间后不可短暂展示上一空间的敏感结果。
- 对象键与路径使用受控稳定标识，不使用用户可编辑显示名称作为权限边界；显示名称可重复、可修改。
- 任务 ID 只做标识，不能不经解析就拼接成可写路径。路径由受信任服务映射并验证根目录约束。
- 删除或断开工作空间前检查运行实例、未提交副本和恢复任务；不能清理仍然唯一保存的用户修改。

### 3.3 本地到远程的迁移

联网个人复用远程团队模型并限制为单成员，不维护第二套远程个人同步引擎。本地到远程采取显式导出、导入、校验和切换权威来源的过程，首期不做自动双向合并。

旧库迁入个人空间时保留稳定 ID、代理关联、内核版本与秘密引用。迁移失败须保留原库和目录，不以静默初始化空库作为容错。

## 4. 本地 SQLite、文件与凭据

### 4.1 SQLite 与 repository

- 所有数据库操作集中到 storage/repository 层；底层 packages 不反向依赖 Electron Renderer。
- 选定一个可审计的 schema 与 migration 权威链路，核对实际 DDL、schema 文件、查询字段和约束，消除多份定义漂移。
- 迁移具备版本记录、重复运行保护、失败恢复和旧数据测试。需要事务的操作整体提交，不能把多个独立 repository 调用当作一个事务。
- 代理变更与关联环境配置更新应在同一数据库事务内保证一致；秘密文件更新则需要额外补偿，因为它不参加 SQLite 事务。
- WAL 模式不是备份机制。使用 SQLite 支持的一致性快照/备份方式，并验证当前 Electron 内置 Node/SQLite 组合能正确执行；不要直接复制正在写入的主文件。[T1]、[T2]
- 对同步驱动的长查询、迁移和备份测量主进程阻塞；确有需要时将数据库所有权迁入专用执行线程，不让多个进程无协调地持有业务写入职责。
- 区分数据库损坏、权限拒绝、磁盘不足和迁移不兼容，提供可见诊断与恢复入口。

### 4.2 浏览器工作目录

每个环境使用独立本地目录，并关联工作空间、环境 ID、内核版本和数据格式。运行锁与进程身份检查需要处理进程崩溃、PID 复用、设备休眠和遗留文件；“锁文件存在”与“浏览器仍在运行”不是等价判断。

对目录进行快照、恢复、删除或迁移前取得同一套业务互斥控制，并确认相关进程停止写入。原子重命名只在满足文件系统条件时可用；跨卷操作必须按复制、校验、切换和失败回滚处理，不能假设所有移动都原子。

### 4.3 秘密保护与可迁移性

| 秘密类型                                      | 保护边界                                                             |
| --------------------------------------------- | -------------------------------------------------------------------- |
| 本地代理密码、个人连接凭据、本机 API 解锁材料 | 使用操作系统安全存储支持的保护；数据库保存引用                       |
| 团队成员数据库/S3 凭据                        | 各成员受限身份，本机安全保存；不共享管理员凭据                       |
| 团队环境共同使用的秘密                        | 需另行验证受授权的存储、发放、轮换和撤销；不能仅共享一个本机凭据引用 |
| 备份密码或解锁材料                            | 用户管理；定时任务需要时经授权安全保存，不写普通配置或日志           |

现有 safeStorage 代码将加密内容存入本机凭据文件，其可用性和保护方式依赖操作系统。[T6] 安全存储不可用时，禁止降级为明文；需要提示用户解锁、重新录入或修复。

不把数据库管理员凭据、S3 管理员密钥或本机控制入口令牌自动装入环境快照。需要随备份迁移的秘密必须有显式范围、导出风险提示和恢复流程；仅复制 safeStorage 密文并不能保证换一台设备后可用。

首期不承诺完整 E2EE。远端共享秘密的具体密钥管理仍是团队权限原型的一部分，不能为了跨机器使用而把普通配置改成明文万能密码表。

### 4.4 v0.1.2 安全修复边界

- 已存代理密码绑定协议、主机、端口和用户名。仅修改显示名称可保留密码；变更连接身份后，测试和保存都要求重新输入密码或明确清除旧密码，不能先保存新目标再借测试接口发送旧秘密。
- Worker 任务标识只允许有长度上限的字母、数字、连字符和下划线，不作为文件路径。公开任务输入不再接受截图路径、输出目录或未声明字段。
- Main 在应用管理的 `worker-results` 根目录下分配随机私有任务目录，以独占方式创建截图文件，将已打开的文件描述符交给 Worker。Worker 只将截图字节写入该描述符，不解析调用方路径，也不按任务 ID 创建文件。
- Main 负责返回截图路径，校验产物身份、文件类型和大小；拒绝 Worker 自报路径。失败、取消和超时清理本次分配的目录；成功产物保留供结果使用。截图上限为 32 MiB，超限明确失败。
- 这些是本机可信应用边界内的安全修复，不承诺阻止已经控制操作系统的同账户攻击者，也不扩展为备份、通用任务平台或团队存储。

## 5. PostgreSQL：身份、授权与受控操作

### 5.1 适用范围与部署边界

PostgreSQL 保存远程工作空间的配置、成员与环境授权、租约、版本索引和必要审计。它不保存整个浏览器目录，也不负责运行浏览器。

用户负责数据库部署、容量、网络可达性、底层备份与运维。项目提供受支持版本范围、初始化与升级说明、角色权限方案、schema/迁移和连通性诊断。管理员执行部署操作与普通成员日常操作使用不同身份。

OWASP 建议不可信厚客户端通过具备访问控制的 API 访问数据库，而不是直接连接。[T5] 本项目不提供独立业务服务端，因此必须明确接受并验证直连所需的数据库侧约束；不能借“用户自托管”回避这项风险。

### 5.2 可信身份是 RLS 的前提

- 不向所有成员发同一个数据库登录身份，再使用客户端自报 `memberId`、`workspaceId` 或可自行设置的 session variable 充当认证。
- 优先验证数据库可识别的独立受限登录主体及其成员映射；如使用代理身份机制，必须证明普通客户端无法伪造认证上下文。
- 设备 ID 用于追踪与占用绑定，不是秘密，也不能替代成员认证。
- 连接池或复用连接不得残留上一主体的角色、事务或授权上下文；无法可靠隔离时不要引入共享跨成员连接池。
- 使用加密连接并验证证书；限制网络暴露和连接权限，普通客户端不得持有 DDL、超级用户或授权管理权限。

### 5.3 行级隔离与函数边界

PostgreSQL 的表所有者、超级用户及具备 `BYPASSRLS` 的角色可能绕过行级策略，不能把开启 RLS 等同于已经隔离。[T3]

实现需要同时审计：

1. 角色继承、登录角色、表所有权、schema 权限与默认授权。
2. RLS 的读条件与写入检查，覆盖环境、代理、授权、版本及引用关系。
3. 直接表写入是否应撤销，仅开放受控函数/事务以维护占用、版本和授权不变量。
4. 跨表关联、全量列表、导出、错误反馈、日志和旁路查询是否泄露未授权数据。
5. 客户端直接执行 SQL、调用不同函数顺序或伪造参数时，策略是否仍然成立。

如果采用 `SECURITY DEFINER`，需要最小所有者权限、安全的 `search_path`、受控函数执行权限以及明确的调用者身份来源。[T4] 不能把函数内部的所有者身份当成真实成员，也不能信任调用参数中声明的 actor。普通客户端不得替换依赖对象或修改函数。

### 5.4 关键事务

申请占用、续租、提交快照、释放占用、分配或撤销环境权限都需要数据库侧检查：主体、资源归属、授权、当前状态和必要的版本条件。

- 使用数据库时间计算租约相关条件，不能信任客户端时钟决定授权是否过期。
- 竞争申请必须原子化，重复请求有稳定结果；不能先查询“无人占用”再无条件写入。
- 快照提交同时检查基础版本、有效租约代次与提交权限，过期客户端不得覆盖新版本。
- 授权表、版本索引和租约不得允许普通成员绕过函数任意改写。
- 迁移由授权管理员协调执行，有 schema 版本门槛与兼容客户端检查，不能由每台成员客户端抢跑 DDL。

具体 SQL、驱动、ORM、角色数量与 PostgreSQL 版本范围仍待原型选定。通过普通 UI 演示不能替代直接 SQL 的对抗测试。

## 6. S3：团队文件授权与对象生命周期

### 6.1 两种兼容等级

| 用途           | 必须验证                                                          |
| -------------- | ----------------------------------------------------------------- |
| S3 备份目的地  | 连接鉴权、上传/下载、校验、失败恢复和受控清理                     |
| 团队 S3 主存储 | 上述能力＋成员/环境授权、撤销、读写分离、已提交对象保护及版本交接 |

团队只支持通过权限验收的后端与部署组合，不承诺所有 S3 兼容服务。兼容的 HTTP 接口或上传成功，不代表具备相同 IAM、临时身份、策略条件或对象版本能力。[T7]

### 6.2 访问控制要求

- 不向所有成员分发相同 S3 管理员密钥，不依赖“对象键难猜”保护文件。
- 每个成员只能访问获授权环境的对象；读、写、列举、删除分别控制。普通成员不能列举全团队敏感对象后再在 UI 中过滤。
- PostgreSQL 授权不能自动阻止 S3 请求。文件权限必须独立验证，尤其要测试绕过桌面直接访问对象的情况。
- 管理员分配/撤销环境权限时，协调数据库与文件授权；不存在天然跨系统事务，需要操作状态、重试与补偿。
- 授权发放部分失败时不宣布环境可用；撤权部分失败时停止正常客户端访问并明确报告残余风险，管理员必须能完成修复。
- 若采用临时凭据或限时访问方式，需要验证签发、有效期与撤销窗口；不能假定“不提供服务端”条件下会自动出现安全签发组件。
- 永久共享密钥加固定前缀不满足按成员撤销的要求。后端无法兑现隔离与撤销时，不列入团队主存储支持矩阵。

### 6.3 快照对象与清理

- 每次快照使用新对象标识；提交后引用固定对象身份、内容哈希和长度，必要时记录后端对象版本 ID。
- 不在原对象上“覆盖保存”。单纯生成不同对象键也不能阻止恶意覆写，已提交对象的不可变性需要后端权限、条件写入或版本策略落实并验证。
- 数据库中的内容摘要用于下载校验，不把所有 S3 实现的 ETag 当作通用 SHA-256。
- 已上传但未提交的对象没有有效版本地位；有效版本以 PostgreSQL 成功提交的索引为准。
- 清理孤立对象或历史版本前核对引用与保留策略，由受限的管理员流程执行，不能让成员随意删除已发布历史。
- 对象不可用或校验失败时拒绝启动该副本，不能自动选择更旧版本并声称已获取最新数据。

S3 日常快照、服务端对象版本和独立灾备分别设计。单桶内保留历史不保证抵御账号失陷、桶删除或基础设施故障。

## 7. 独占运行、租约与版本栅栏

### 7.1 需要同时解决两个问题

1. **使用独占：** 在支持的客户端与已公布的故障条件内，同一环境不能同时出现两个有效运行实例。
2. **提交隔离：** 即使出现旧进程、网络分区或延迟请求，过期持有者也不能覆盖后来提交的有效数据。

数据库租约与递增代次可以帮助实现第二项，但不能单独证明第一项。租约过期不等于操作系统上的浏览器已经停止。

### 7.2 目标占用信息

租约至少关联工作空间、环境、成员、设备、运行会话、基础快照版本、数据库侧到期时间与递增代次。每次取得新资格时发放新代次；续租、提交与释放都核对持有者和代次。

事务使用条件更新或受控函数拒绝陈旧请求。幂等操作标识用于查证网络中断前的结果，不能因重试创建两个会话或重复发布版本。

### 7.3 客户端监督与故障规则

| 事件          | 技术要求                                                                   |
| ------------- | -------------------------------------------------------------------------- |
| 启动前        | 在线确认成员、环境授权、存储可用与占用资格；缓存不能替代授权               |
| 运行期间      | 监督浏览器进程，周期性核对租约与授权，不仅靠页面计时器                     |
| 数据库断连    | 记录连接状态、提示并重连；宽限期届满停止任务并关闭浏览器                   |
| 已确认撤权    | 立即触发受保护任务停止和浏览器关闭，不等待断网宽限期                       |
| 系统休眠/恢复 | 恢复后先核验授权和占用，再允许继续受控操作；测试浏览器恢复先于监督器的风险 |
| 关闭失败      | 记录并告警，不伪报已停止，不直接将未知实例标为可安全接管                   |
| 应用崩溃      | 下次启动核对真实进程、会话、锁、远端租约与本地修改，不直接释放所有遗留状态 |

续租频率、租约 TTL、断网宽限、关闭超时与新实例接管条件必须联合设计。默认优先保护数据和独占，旧实例状态无法确认时不把自动接管当作安全操作。异常接管的证明条件、管理员确认及风险提示在团队原型中确定。

这些机制不能保证关闭恶意客户端、用户手工启动的已复制目录或被控制的操作系统。若正常受支持客户端在休眠/网络分区测试中仍无法满足已声明的独占条件，应阻塞该能力或重新确认限制，不能只让列表显示“独占”。

## 8. 快照发布与本地恢复一致性

### 8.1 正常交接协议

```text
在线验权与申请占用
  → 获取最新已提交版本
  → 下载、校验、准备本地工作副本
  → 启动与监督浏览器
  → 关闭并确认停写
  → 创建快照并上传新对象
  → 条件提交数据库版本索引
  → 确认提交结果并释放占用
```

下载失败、停写失败、未完成校验时不能跳过中间步骤。团队共享文件不直接作为多个浏览器同时写入的用户目录。

### 8.2 数据库与对象存储之间的提交

PostgreSQL 与 S3 没有天然联合事务，采用“先准备对象，再条件发布引用”的工作流：

1. 在绑定环境、基础版本和占用代次的上下文中生成 manifest、内容摘要和唯一操作标识。
2. 上传新对象，验证完整性与可取得性；此时仅是候选对象。
3. 调用受控数据库提交操作，检查授权、租约、基础版本与对象元信息，成功后成为有效新版本。
4. 若响应丢失，按操作标识查询已提交事实，而不是直接覆盖或再次生成版本。
5. 提交失败则保留本地副本，标记冲突或待处理；候选对象进入可审计的清理流程。

数据库提交成功只是发布关系的一环。消费者仍校验对象内容；S3 授权和已提交对象防覆写是独立前置条件。不能让客户端提交一个对象键就推导为永久可用、不可篡改或已经经过服务端内容验证。

### 8.3 本地副本与故障恢复

本地工作副本至少区分“与某已提交版本一致”“存在本地修改”“上传中”“等待提交确认”“冲突/失败”这些事实，具体枚举在 contracts 中设计。

上传失败时不能删掉唯一的新数据；失败后释放占用或被接管，需要保留本地分支并明确它不能自动覆盖当前有效版本。重新获得资格后，也必须重新比对基础版本。

恢复通过受控暂存目录、完整性预检、旧副本保留和可恢复的切换记录完成。数据库变更与文件切换同样没有天然跨系统事务，需要记录阶段并在崩溃后补偿，不能只依赖 `try/finally`。

首期使用全量快照并排除经验证可重建缓存。按三平台测量快照体积、压缩时间、上传耗时和磁盘峰值后，再决定是否引入增量、去重和专用文件服务；不提前假设大型目录适合任意网络。

## 9. 备份引擎、加密与定时任务

### 9.1 统一逻辑格式，分离渠道

备份任务先定义捕获范围与一致性边界，再生成逻辑包；本地、OpenList、S3 只负责目的地传输与必要的状态管理。提供方之间共用格式校验和恢复逻辑，不维护三套不兼容备份格式。

manifest 至少描述：格式版本、应用/schema 版本、工作空间与环境范围、配置修订、内核/平台信息、文件清单、大小、摘要、排除项与秘密处理方式。校验值不等同于可信签名，未加密包也不能仅因自带哈希就当作来自可信来源。

首期完整备份可以按工作空间或环境构建明确单元。部分环境正在运行时，定时任务延后这些单元并报告部分结果，不能把一份持续变化的整库与不同时刻的文件拼在一起，宣称取得了同一时点全量快照。

### 9.2 渠道适配与参考边界

| 渠道     | 实现要求                                                                                        |
| -------- | ----------------------------------------------------------------------------------------------- |
| 本地     | 受控目的地、空间预检、临时写入、校验后发布；源目录和目的地不能形成递归备份                      |
| OpenList | 核验部署版本、实际 API/WebDAV 能力、认证方式、目录权限、上传完成语义与失败恢复                  |
| S3       | 核验端点、凭据、桶/前缀权限、分片上传清理、对象校验及保留清理；备份权限不自动复用团队管理员权限 |

OpenList 官方 WebDAV 文档描述账号密码等认证配置。[T8] 参考项目中的 token 或特定 API 用法不能当作所有部署都支持的标准，协议和凭据组合需加入兼容矩阵。

按维护者要求参考 Ant Browser 的备份清单、暂存发布、校验和恢复流程，研究快照见项目规划。只借鉴经过理解的设计，不默认复制代码、许可或认证实现；其某个渠道有定时任务，不代表所有渠道都有相同能力。

### 9.3 可选加密

- 本地、OpenList、S3 都支持关闭或开启备份包加密；远端连接凭据不代替包级密码。
- 开启时支持用户输入或使用密码学安全随机源生成密码，不使用普通伪随机数生成器。
- 采用成熟、经过审视的认证加密与密码派生方案；具体算法、库、参数、格式与兼容策略在实施前选定，不自研密码学。
- 每个包记录必要的格式/KDF 元信息，使用独立随机材料；解密前对参数设资源上限，避免恶意包耗尽内存或 CPU。
- 加密范围应覆盖敏感内容及必要的 manifest 元数据，未加密外层头部只保留识别和解锁所需最少信息；解密成功仍需业务格式校验。
- 错误密码、篡改、截断、超大参数和不支持版本必须安全失败，不能生成“部分恢复成功”的可运行目录。
- 不提供官方密码找回；定时备份需要保存解锁材料时征得用户同意并使用本机安全保护。
- 关闭加密必须清晰提示敏感内容风险；具体秘密导出范围和本地开关默认值仍待设计。不能在用户选择加密后因凭据不可用而改传明文。

ZIP、压缩、HTTPS、S3 access key 或文件 SHA-256 各自解决不同问题，不能当作备份包内容加密的替代品。

### 9.4 应用内调度

调度器由应用生命周期拥有，保存任务配置、执行记录与错误状态，而不是使用 Renderer 组件定时器维持任务。完全退出时停止调度并安全取消或收尾当前任务，不安装常驻系统服务，不安排操作系统唤醒应用。

任务执行前检查目的地、磁盘、网络、授权、密码材料、环境停写与同一资源的互斥条件。运行中环境首期默认延后；若用户主动选择关闭后备份，应明确显示这是用户操作，不能变成定时任务的隐式行为。

漏跑补做、时区变化、夏令时、睡眠唤醒、重复触发、重试退避、保留数量与并发上限需在调度设计中确定并测试。定时配置可保存，但不意味着已承诺退出期间执行。

### 9.5 恢复安全与团队完整备份

- 所有恢复都先做格式、摘要、大小、路径和兼容检查；拒绝绝对路径、目录穿越、符号链接逃逸及解压膨胀攻击。
- 在受控暂存区完成验证后再切换目标，保留旧副本及失败恢复记录；不将归档内脚本或二进制当作可信安装内容自动执行。
- 内核包、浏览器用户目录和工作空间数据库分别核对格式与版本，不因为其中一项可降级就认为其余都可回退。
- 跨系统恢复可能因浏览器或 OS 的秘密绑定需要重新登录，不能承诺任何站点会话都可迁移。
- 团队全量备份/恢复/历史删除只能由授权管理员执行；普通成员备份权限不能扩大到未分配环境。
- 团队首期使用维护窗口暂停相关写入，捕获一致的 PostgreSQL 业务数据及引用对象集合，恢复时在隔离目标核验两者对应关系。
- 基础设施物理备份和应用级导出职责分别说明；工作快照上传成功不代表完成灾备。

## 10. 内核接入、扩展与网络能力

### 10.1 上游选择与能力验证

首发正式提供方数量为一个，优先验证已接入的 `adryfish/fingerprint-chromium`。项目不维护其源码分支，也不默认承担上游未提供的系统产物构建职责。[T9]

当前 Adapter 目录版本为 `148.0.7778.215`，内置包映射只有 Windows x64 和 macOS ARM64；macOS Intel x64 是发布前必须补齐的缺口。核验合格发行物后再补映射，不能以管理界面能运行、manifest 返回了 capability 或标准 Chromium 可启动来替代验收。

每个提供方的能力表区分：声明、接入、自动测试、实机验证和已知限制。指纹配置的保存值与浏览器观察到的有效值分开记录；保持身份稳定不等于声称所有暴露面都可控制。

### 10.2 下载、安装与版本维护

- manifest 记录提供方、来源、发行版本、OS/架构、许可证信息、包类型、预期文件与可信渠道的 SHA-256。
- 下载限制来源与重定向、超时、文件大小和磁盘占用，支持取消；先写临时文件，验证后安装。
- ZIP、DMG 等包型按平台隔离实现并测试，不能将任意下载路径、文件名或执行文件交给 Renderer 决定。
- 安装只发布已校验目录；升级保留可识别的旧内核与回退路径，检查环境目录格式兼容性。
- 校验失败、来源未知、架构不符或许可未核实时，不执行二进制。
- 上游仓库开放不证明某二进制与源码可复现对应；源码提供方式、补丁可用性、再分发条件与第三方 notices 单独核验。
- 本轮不承诺特定版本永远可下载。上游不可用时提供明确错误和恢复说明，不绕过校验改用未知镜像。

### 10.3 指纹、代理与扩展

- 提供方专属参数放在 Adapter 中，业务层保存稳定配置及 schema 版本，不让页面拼接任意内核命令行。
- 代理目标与其秘密引用必须绑定，修改目标时不能复用不属于新目标的已存密码去测试连接。
- 语言、时区、代理和指纹分别校验；不支持的参数显示限制，不能静默忽略后报告成功。
- 不把代理密码放进命令行、URL 或日志；如使用本机认证桥接服务，限制监听范围、进程生命周期及凭据暴露，并验证实际内核行为。
- 支持兼容的 Chromium 扩展及开发者模式加载未打包/已解压扩展；Chrome 网上应用店直装不是首发硬性门槛。[T10]
- 扩展资源、路径、权限及恢复方式明确记录，不把旧机器绝对路径视作可跨设备的安装信息。

### 10.4 CDP 与控制面

浏览器调试接口应只绑定 loopback，使用随机端口，并限制生命周期与暴露范围。原生 CDP 并不会因为随机端口就自动具备认证；不能虚构“给一个一次性 token 就保护了所有原生调试连接”。

应用自行提供的控制接口必须有明确身份与授权，不能把原生 CDP 端口暴露为无校验的公共能力。根据提供方能力评估 pipe、本机受控代理或其他隔离方式；在无法完全隔离同机恶意进程时如实记录残余风险。工程规范的一次性凭据要求不能靠给原生接口加一个未被实现的字段来声称满足。

需要多个控制工具接入时，由运行服务协调会话、认证桥接、事件订阅和退出处理。CDP 命令回复超时与网页 HTTP 请求耗时分别处理，不能混为同一故障条件。

## 11. Local API、CLI、MCP：个人首发交付

### 11.1 共享命令，不复制业务

三个入口与 GUI 共用同一命令层、contracts、错误码、任务、路径解析和环境锁；后续进入团队模式时继续执行同一授权和独占规则。禁止另开“开发者接口”绕过权限。

首发最小契约应能完成环境发现、受控启停、运行或任务状态查询；名称、输入输出与版本机制在工作包设计中固定。长操作返回任务标识并允许查询、取消，不能靠一个无期限 HTTP 请求或 UI 页面维持。

### 11.2 传输与安全待选项

| 入口      | 设计约束                                                                         | 待验证选择                                                   |
| --------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Local API | 仅本机、显式启用与身份校验；不开放任意文件、SQL、命令或 CDP 转发                 | 本机 HTTP 或等价受控传输、令牌生命周期、客户端来源校验       |
| CLI       | 通过受支持本机入口调用应用，不直接打开业务数据库或绕过锁；明确退出码和结构化结果 | 命令布局、连接发现、输出格式                                 |
| MCP       | 暴露经过授权的有限工具；请求仍受命令层校验；不信任调用模型的意图声明             | 优先评估本机 stdio；具体 SDK、传输及授权机制在首发实现前选定 |

若采用 HTTP，需测试 loopback 绑定、来源和 Host 检查、跨站请求、DNS rebinding、令牌泄露与并发重放；不能以“仅本机”作为免认证理由。秘密不能通过 URL、普通日志或命令行明文传递。

应用完全退出时，本机命令服务与备份调度一起停止。CLI/MCP 遇应用未运行时应给出明确错误或走另行设计的显式启动流程，不偷偷创建独立常驻守护进程。

Local API 是桌面应用的本机控制入口，不是本规划排除的团队业务服务端。交付这三个基础入口也不等于已经交付完整可视化工作流。

## 12. 前端、后续自动化与 AI 边界

### 12.1 前端继续渐进复用

React 页面按环境、代理、内核、工作空间、备份等领域组合，数据请求与提交副作用进入 feature/service 层；路由组件不直接拼接 SQL、文件路径或内核参数。

TanStack Query 管理查询与失效，表单库管理输入与校验，组件状态保存短期交互；任务事实来自后台服务。工作空间切换、权限撤销、断连、部分备份与未提交修改都需要明确的界面状态和错误恢复路径。

现有组件、主题、日志和手动更新功能按实际可用性保留。本轮不重新指定视觉主题，不把某个精确刷新间隔或页面尺寸写成长期架构规则，也不为规划重写批量升级 UI 依赖。

### 12.2 进阶工作流

先把基础命令、任务生命周期、幂等、超时、取消、恢复和结果持久化做可靠，再在真实需求下决定可视化编排。画布不是执行器，不能通过增加节点组件替代任务可靠性。

首期不引入分布式队列或远程执行集群。是否需要 React Flow、专用执行引擎、增量存储等，基于阶段目标、性能证据与单人维护成本单独评估。

### 12.3 AI 与开发测试

AI 和网页内容均不能成为可信授权来源。网页提示、工具结果和模型输出不得绕过用户授权、环境分配、秘密访问、下载上传和危险操作确认。

模型提供方、密钥归属、数据外发提示、成本控制、工具确认、结果评估和 SDK 在进入 AI 工作包前再设计。不要提前部署向量数据库、RAG 服务或多个编排框架。

网站测试与开发调试复用已验证环境及任务接口，再根据真实场景扩展报告、追踪和断言。进阶工作流、AI 与开发测试的具体交付先后仍以项目规划为准，不在技术栈文档中另开一条固定路线。

## 13. 验证、迁移与发布

### 13.1 验证分层

| 层级       | 重点                                                                   |
| ---------- | ---------------------------------------------------------------------- |
| 单元与契约 | schema、命令、IPC 请求响应、错误、路径限制、任务与 Worker 协议         |
| 本地集成   | SQLite 迁移、代理/环境事务、秘密文件补偿、进程锁与启动恢复             |
| 备份集成   | 三渠道、加密与不加密、停写、损坏包、错误密码、空间不足、取消与中断恢复 |
| 远程集成   | 普通账号直接 SQL、S3 直接请求、跨团队隔离、授权/撤销部分失败           |
| 并发与故障 | 竞争启动、租约失效、陈旧提交、响应丢失、断网、休眠与关闭失败           |
| 三平台实机 | 内核安装、实际指纹/网络/扩展行为、持久化、备份恢复与控制入口           |
| 发布验收   | 许可、来源、签名状态、安装包、升级兼容与恢复演练                       |

测试夹具不使用真实账号、Cookie 或个人目录。常规单元测试不依赖上游临时可用；需要下载内核或实际基础设施的测试单独标明条件和成本，不能把未执行项显示为通过。

BUGS 报告先复现再分类。当前重点包括代理目标与秘密绑定、Worker 标识路径、跨实体事务、初始化失败和窗口恢复；报告中的旧产物测量、旧规范冲突或不精确描述不能直接成为测试结论。

### 13.2 当前检查命令与覆盖边界

仓库已有以下检查入口，执行结果应记录到对应变更中：

```sh
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test
```

当前根 `format:check` 只调用桌面包格式检查，不自动覆盖根 `docs`。文档改动需要额外检查，例如在桌面包工作目录下执行：

```sh
pnpm exec prettier --config .prettierrc.json --check ../../docs/project-plan.md ../../docs/technology-stack.md ../../docs/version-roadmap.md
```

`pnpm test:desktop` 和 `pnpm test:fingerprint` 是现有 smoke 入口，需先核验脚本前提并在合适设备执行。脚本存在、某次单元测试通过或某个平台构建成功，都不能替代完整产品验收。

### 13.3 兼容与升级

- 应用版本、SQLite/PostgreSQL schema、contracts/控制接口、快照/备份格式、内核版本分别管理兼容范围。
- 拒绝不受支持的写入组合，不能让旧客户端打开新 schema 后继续写入。
- 本地 migration 保留迁移前恢复点；团队 migration 由管理员协调、锁定并记录结果。
- 应用回退、数据库回退、内核回退与用户目录恢复是四件不同的事，分别说明可行范围。
- 现有手动更新实现按固定来源、校验、用户确认和取消边界复核；不因重写文档就自动改成后台升级。
- 内核升级先做兼容检查，不强制在未知格式上启动并破坏用户目录。

### 13.4 依赖、许可与发布产物

引入或更换库前记录用途、许可证、原生模块、网络行为、遥测、替换成本和验证结果。Node 开发工具链、Electron 内置运行时、原生 ABI 与目标 OS/架构分别核验。

开源目标尚需维护者选择并补齐根许可证；不擅自将项目标为 MIT 或 AGPL。第三方代码、内核二进制、字体和扩展另行核验，不能用应用许可证覆盖它们。

三平台正式发布分别记录签名/公证状态、下载来源、产物校验与已知限制。SBOM 和包体分析面向实际产物，旧 alpha 数据不能替代当前结果。构建任务最小权限、发布秘密保护与依赖风险检查需要在发布工作包中验收。

## 14. 实施决策与阻塞项

| 决策/验证项                       | 所需证据                                        | 未通过时的处理                                                 |
| --------------------------------- | ----------------------------------------------- | -------------------------------------------------------------- |
| 三平台指纹提供方                  | 合格发行物、来源与许可、实际行为、升级/恢复结果 | 阻塞对应平台正式支持；重评提供方，不默认维护源码或无声取消平台 |
| 本地 schema 与 migration 权威链路 | 旧库升级、失败恢复、repository 与定义一致性测试 | 先修本地数据层，不用备份功能掩盖已有损坏风险                   |
| PostgreSQL 身份与权限             | 受限主体、直接 SQL、RLS/函数/角色绕过测试       | 不发布团队权限功能，不以 UI 隐藏替代                           |
| S3 成员授权与撤销                 | 直接对象请求、权限变化、不可变引用、清理权限    | 限制兼容部署矩阵，不能复用全体管理员密钥                       |
| 团队共享秘密                      | 发放、使用、轮换、撤销与备份恢复测试            | 不把本机安全存储引用当作跨设备共享方案                         |
| 租约与实际浏览器独占              | 网络分区、休眠、关闭失败、未知实例接管测试      | 阻塞相关交接能力，明确报告不能证明的保证                       |
| 快照与跨存储提交                  | 断点、响应丢失、陈旧提交、孤立对象与恢复演练    | 保留本地数据，不宣称已同步                                     |
| 备份格式与密码学                  | 可靠库选型、跨版本恢复、篡改/资源上限测试       | 不提供自研加密或静默明文回退                                   |
| 本机控制契约                      | GUI/Local API/CLI/MCP 等价行为和越权测试        | 仍属个人首发未完成，不挪到“后续预留”                           |
| 发布许可与可信安装                | 维护者许可决定、第三方清单、三平台安装证据      | 明确阻塞或限制，不把代码公开等同完整开源发布                   |

这些项目需要后续实现工作包提供证据，决策时点与版本门槛在[版本迭代计划第 16 节](version-roadmap.md)追踪。失败时保持相关版本线阻塞，不用 UI 限制或缩小未说明的范围换取通过。文档规划不添加空 package、不安装候选依赖、不改生产配置，也不宣称上述原型或验收已经完成。
