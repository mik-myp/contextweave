## 1. 版本迭代规则

### 1.1 一条版本线完成，再进入下一条

采用维护者要求的方式推进：

```text
规划起点 v0.1.1
  → v0.1.2 → v0.1.3 → …… → v0.1.x 完成门槛
  → v0.2.0 → v0.2.1 → …… → v0.2.x 完成门槛
  → v0.3.0 → ……
```

- **版本线**指 `v0.1.x`、`v0.2.x` 等；每条线有一个明确主题和冻结范围。
- **小版本**指该线内一次可交付的增量；`.0` 是新版本线的第一个交付，不是整条线的全部能力。
- 前一条版本线全部必选目标、回归与门槛通过，才把开发主线切换到下一条。不能把没做完的首发功能随意改成“以后再做”。
- 下表列出目前可识别的小版本。若最后一个编号结束后仍未完成，继续追加同线小版本，例如 `v0.1.8`，不能因为编号用完而放行。
- 同一小版本太大时可以继续拆小，但要同步后续编号、依赖和验收，不能悄悄缩小目标。
- 每次发布应能安装、升级和使用本次开放的功能；内部接口或空页面不算用户功能交付。
- 不要求人为发布没有代码或行为变化的空补丁。预留反馈补丁没有实际问题时，记录“不需发布”及验收证据，不伪造一次修复。
- 版本线完成指**已冻结范围**完成，不是证明永远没有新缺陷。后续发现的安全问题仍可回补旧线，但不借此无限拖延或跳过已知阻塞项。

### 1.2 编号、试用与兼容性

- `v0.1.0`、既有 alpha 和 `v0.1.1` 是历史事实，不改名、不重写 tag，不把新范围追记为过去已经实现。
- 本规划的“个人版首次完整交付”安排在 `v1.0.0`：表示首次满足重写后的全部个人版要求，不否认旧版本已经发布。
- 小版本号用于细粒度交付组织，不能仅凭补丁位推导数据库、内核目录或公共接口一定兼容；每次发布必须给出实际兼容范围。
- 进入稳定阶段后，已公开接口和数据的破坏性变化不得隐藏在小补丁中，必须重新审查迁移、版本策略和发布说明。
- 每个目标版本可以先发布 `-alpha.N`、`-beta.N` 或 `-rc.N` 进行测试；预发布后缀不替代该版本的完成门槛。
- 团队功能在正式验收前仅面向明确知情的测试者和测试数据。不能因同一安装包的个人功能稳定，就把实验性团队能力称为正式支持。
- 不制定未经确认的日历期限。由一位维护者顺序推进，同伴提供测试反馈，不依赖多人并行开发。

### 1.3 所有小版本的共同完成条件

下面条件适用于所有版本，后续表格只写该版本额外要求：

1. contracts、UI、后台服务、存储与文档在实际开放范围内连通；没有“页面能点但后台未实现”的假完成。
2. `pnpm check` 通过，变更 Markdown 另做格式与链接检查；新增行为补与风险相匹配的测试。
3. 涉及数据或文件结构时，覆盖从上一受支持版本升级、迁移失败、恢复与不兼容拒绝；不得默默清空数据。
4. 相关失败、取消、重试、重复操作和异常退出有明确结果；秘密、路径与权限边界没有已知未处理的高风险缺口。
5. 记录测试环境、步骤、结果、已知限制及证据。自动测试通过不能代替真实内核、安装包与三平台验收。
6. 所需维护者决定已落地；未定许可证、密码格式、权限身份或兼容后端等事项不能用默认猜测完成验收。
7. 该版本目标确实有变化时才发布；未完成时留在当前版本线，更新阻塞原因与下一次验证动作。

### 1.4 持续开发与发布授权（2026-09-26，Asia/Shanghai）

维护者要求从当前版本连续开发到 `v1.0.2`，该指令替代此前“每次发布后暂停等待确认”的执行方式，不改变产品边界和工程质量门槛。

1. 所有开发在 `master` 顺序完成，不开启子智能体、不强制推送或重写已发布 tag；原有 `README.md`、`BUGS.md` 用户改动保持原样，不混入提交。
2. 每版按本台账冻结范围实现并回归，提交/推送 `master`，核对对应提交的 CI 与三平台构建后再创建版本 tag 和 Release；发布说明包含实际变化、迁移/兼容、证据和已知限制。
3. 核验 Release 构建、安装附件和摘要，补齐实施台账后直接进入下一小版本，不再索取逐版确认；到 `v1.0.2` 后停止，等待维护者统一确认。
4. 不以递增版本号代替功能完成，不跳过仍阻塞下一版本线的安全、恢复、平台或许可问题，不为“按反馈发布”的预留版本编造问题或空发布。反馈尚未收到时如实记录；维护者尚未决定的许可证等事项仍不能代为授权。
5. 失败的 CI/构建先定位并修复，网络类外部失败可以有记录地重跑；无法继续的外部前提或必须由维护者决定的事项明确说明，不悄悄降低门槛。
6. 每次接续工作先核对工作区、远端 `master`、tag、Release 与台账，避免重复发布；已存在 tag 不移动。新规则不改写历史版本当时的等待与验收记录。

### 2.3 对已有检查结论的修正

- `BUGS.md` 仍是问题输入，不是全部已复现的事实。本次不修改报告，也不宣称修复其问题。
- 当前批量执行已经记录 `succeeded` 和 `failures`，界面有进度和部分失败提示；差距是后台批次任务的所有权、持久化、取消及恢复，不应再写成“完全没有部分失败反馈”。
- 当前存在 `theme-provider.test.tsx`、`use-data-table.test.tsx`、`data-table-row-actions.test.tsx` 等组件/hook 测试；应补关键页面和跨进程路径，不应再写成“所有组件测试都是零”。
- SQLite 迁移已有一致性安全副本，但并没有用户可选的三渠道备份；回收站恢复也不是灾备恢复。
- 发布矩阵有 Intel Mac 构建目标，但官方指纹 smoke 跳过该架构。不能由此认定三平台指纹支持已经完成。
- 指纹页目前是重定向，TeamSwitcher 是预留，Worker smoke 是开发能力：三者都不能当成完整产品模块。

1. **批量新增代理：** 一行一项，支持 HTTP、HTTPS、SOCKS5，以及 `socket5`/`socks5h` 输入别名；支持 URI 和 `host:port:username:password`、默认协议、IPv6 与凭据百分号编码。一次最多 200 行/65536 字符；按行隔离错误，重复连接跳过且不覆盖密码。Main 复用安全保存/补偿，结果不回传原始 URI。界面只保留失败行供修正重试。
2. **代理检测：** 参考 Ant Browser 源码快照 `61feab721f71d65301dfa45397cb9e15e28e8fd8` 的 `backend/internal/proxy/speedtest.go`：其默认目标为 HTTP gstatic 204，本项目原先要求 HTTPS ipify 返回有效出口 IP。现在依次探测 HTTPS IP、HTTPS 连通性、HTTP 连通性；HTTP 使用绝对 URI 普通代理转发（不强制 CONNECT），HTTPS 才使用 CONNECT，每步限时/限大小，总预算 15 秒；均经受控认证代理，不直连、不关闭 TLS。界面区分 HTTP-only、HTTPS 与未能查询出口 IP。未取得维护者所述真实代理，不能声称已复测同一条代理。
3. **环境关闭与恢复：** 原生 profile session 恢复上次标签，关闭 Chromium 后台模式；最后一个顶层页面关闭后延迟复核并有序停止。正常 CDP 断开等待进程退出，不误报崩溃；自动停止完成前的新启动等待旧资源释放。活动记录区分浏览器关闭与用户停止。
4. **应用更新：** 检查后点击“下载、安装并重启”即可继续完整流程；安装前复核 SHA-256 和运行环境。Windows 安装版使用 NSIS 更新参数；macOS 使用只读 DMG、身份/架构/安全链接检查、同卷暂存及独立 helper。没有运行环境时正常退出，再替换和启动；保留权限、签名、便携版、开发运行等明确失败边界。挂载异常不递归删除挂载点；替换中失败恢复旧 app，但新代码启动后不自动降级数据。`v0.1.2 → v0.1.3` 仍用旧更新器，自动安装功能从运行本版后生效。macOS 安装旁的旧 app 副本目前需确认升级正常后人工清理，不是数据备份。
