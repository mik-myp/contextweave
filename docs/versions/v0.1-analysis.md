# ContextWeave v0.1 版本分析

**修订号：** r2
**状态：** 已完成分析，执行文档 r6 已确认，开发中
**适用范围：** v0.1 前置分析，不是已批准的执行文档
**分析日期：** 2026-09-21

本文档根据已确认的项目规划、技术栈和开发流程生成，并已整理为用户确认的 `v0.1-execution-r6.md`。它记录分析背景，不替代当前执行文档。

## 1. 本阶段目标

v0.1 的目标应是建立可发布的桌面客户端基础，并验证“独立浏览器内核 + 环境生命周期 + 本地任务协调”这条最小技术链路，为后续个人环境管理、团队服务和环境接力保留稳定接口。

项目总体规划当前给出的 v0.1 候选范围为：

- Electron 客户端可以启动和关闭。
- 本地个人空间可以创建一个浏览器环境。
- 环境拥有独立用户数据目录、运行锁和状态记录。
- 可以注册、下载、校验和启动至少两个浏览器内核。
- 每个内核通过自己的 manifest、配置 schema 和 adapter 暴露能力。
- 可以配置最小代理和指纹参数，并在启动前完成校验。
- 可以启动、停止、查询外部浏览器进程，并处理异常退出。
- 独立 TypeScript Worker 可以完成一个最小可验证任务。
- GitHub Actions 可以构建 Windows 和 macOS 未签名产物并生成 SHA-256。
- 记录启动耗时、内存、下载失败和浏览器异常等基础诊断信息。

上述内容是候选范围，不代表已经批准。

## 2. 建议的 v0.1 非目标

以下内容建议不进入 v0.1，除非用户明确要求并重新评估范围：

- 团队 API、NestJS、PostgreSQL、对象存储和成员邀请。
- 团队环境租约、环境接力、跨设备快照同步。
- 完整备份恢复、增量快照和跨系统 profile 迁移。
- 可视化工作流编辑器、商品巡检、订单报表、网站测试和数据采集模板。
- LangChain、LangGraph、RAG、AI Agent 和远程执行节点。
- 完整 WebUI、自动更新、代码签名和 macOS 公证。
- 插件市场、微服务、Redis、Temporal、Kubernetes 和复杂调度。

v0.1 可以提前定义 contracts、资源 ID、事件和版本字段，但不实现后续业务。

## 3. 技术边界

```text
Electron Renderer
    ↓ 类型化 Preload API
Electron Main / 本地协调层
    ├── SQLite 元数据
    ├── 环境目录与运行锁
    ├── Kernel Registry
    ├── Kernel Adapter
    └── 独立浏览器进程

独立 TypeScript Worker
    └── 通过版本化协议执行最小任务
```

需要保持的边界：

- Electron 自带 Chromium 只渲染管理界面，不能作为指纹浏览器内核。
- 浏览器内核必须是外部进程，使用独立用户目录和独立控制端口。
- Renderer 不直接访问文件系统、数据库或任意 CDP 端口。
- 内核专属参数只出现在 manifest、schema、adapter 和对应测试中。
- 内核版本与 Electron 客户端版本独立记录。
- v0.1 不连接 PostgreSQL，也不实现团队客户端协议，除非执行文档另行批准。

## 4. 候选用户闭环

### 4.1 本地个人闭环

```text
下载 Release
→ 启动客户端
→ 创建个人环境
→ 选择内核
→ 配置代理和最小环境参数
→ 下载并校验内核
→ 启动浏览器
→ 打开测试页面
→ 查询状态
→ 停止浏览器
→ 再次启动并恢复环境
```

### 4.2 异常闭环

```text
下载中断 / 校验失败 / 启动失败 / 浏览器崩溃 / 重复启动
→ 显示可理解的错误
→ 清理临时资源和运行锁
→ 保留诊断信息
→ 允许安全重试或恢复
```

### 4.3 Worker 最小闭环（待确认）

建议 Worker 只做一个确定性任务，例如打开指定 URL、读取页面标题、截图并返回结构化结果；不在 v0.1 引入工作流画布或 AI。

## 5. 候选内核方案

v0.1 至少验证两个内核，但需要用户确认具体组合：

- 方案 A：`fingerprint-chromium` + 标准 Chromium/Chrome/Edge。
- 方案 B：`fingerprint-chromium` + Camoufox。
- 方案 C：标准 Chromium/Chrome/Edge + Camoufox。

推荐先选择方案 A：两个内核都以 Chromium/CDP 为主，能先验证 Registry、manifest、下载、启动、代理和用户目录边界；Camoufox 作为后续独立适配，避免 v0.1 同时承担 Firefox 家族协议和指纹配置差异。

无论选择哪一组，内核分发都应采用：manifest → 平台/架构匹配 → 临时下载 → SHA-256 校验 → 原子安装 → 启动。

## 6. 初步风险

| 风险 | 影响 | v0.1 处理建议 |
|---|---|---|
| 第三方内核来源或许可证变化 | 无法稳定下载或发布 | 记录来源、许可证、版本和哈希；不把下载地址写死在 UI |
| 内核参数实际不生效 | 用户以为已完成指纹配置 | 只暴露已验证能力；用能力检查和测试页面验证 |
| 浏览器进程残留或锁未释放 | 环境损坏或重复写入 | PID、进程状态、锁超时和异常恢复测试 |
| 下载包损坏或被替换 | 执行不可信文件 | HTTPS、SHA-256、原子安装、失败清理 |
| Electron IPC 权限过大 | 本地数据和进程被网页利用 | contextIsolation、sandbox、Preload 白名单和参数校验 |
| Worker 卡住拖垮客户端 | UI 无响应或资源泄漏 | 独立进程、超时、取消、退出清理和日志 |
| Windows/macOS 差异 | Release 可下载但无法运行 | 维护平台/架构矩阵，使用干净环境启动验证 |
| 未签名安装包拦截 | 用户无法首次启动 | Release 提供首次启动说明和 SHA-256 |

## 7. v0.1 暂定验收方向

以下是待确认的验收草案：

- 在目标支持平台上，用户无需安装 Node.js、Python 或开发工具即可启动客户端。
- 可以创建一个环境，环境目录和其他环境隔离。
- 至少两个已确认内核可注册、下载、校验、启动和停止。
- 不支持的内核参数会在启动前提示，不会静默忽略。
- 代理配置失败、内核下载失败、浏览器崩溃和重复启动都有明确反馈。
- Worker 最小任务可以成功、超时、取消和失败，并保留结构化事件。
- 应用关闭后再次启动，环境元数据和状态可以恢复；不会把运行中的浏览器误判为可安全接管。
- Windows 和 macOS 目标产物由 GitHub Actions 构建，并生成 SHA-256 文件。
- 关键测试、构建结果、产物哈希和已知限制写入 `docs/progress/v0.1.md`。

## 8. 原始待确认问题（已由用户回答）

以下问题用于形成 v0.1 执行边界，用户已确认全部推荐方案；推荐答案和最终决定分别保留在本节和第 9 节。

1. **v0.1 是否严格只做个人本地模式？**
   - 推荐：是。团队 API、PostgreSQL、成员和租约从 v0.4 开始；v0.1 只预留接口和 ID 字段。

2. **v0.1 验证哪两个内核？**
   - 推荐：`fingerprint-chromium` + 标准 Chromium/Chrome/Edge。
   - 如果希望尽早验证 Firefox 家族适配，也可以选择 Camoufox，但会增加协议、配置和测试范围。

3. **内核下载来源采用什么方式？**
   - 推荐：v0.1 使用项目维护的版本化 manifest 和用户触发下载；不在仓库提交大体积二进制，不提供未经核验的动态 URL。
   - 需要确认：是否允许用户通过设置添加自定义 manifest/本地内核目录。

4. **v0.1 支持哪些平台和架构？**
   - 推荐：Windows x64；macOS arm64 和 x64 构建并进行启动验证。
   - 需要确认：是否把 macOS x64 只作为构建产物，暂不列为正式支持平台。

5. **代理范围是什么？**
   - 推荐：HTTP、HTTPS、SOCKS5，支持认证；每个环境绑定一个代理；先做连通性检查，不实现代理池和自动轮换。

6. **最小指纹配置包含哪些字段？**
   - 推荐：语言、时区、User-Agent/Client Hints、平台、窗口尺寸、硬件并发数、WebRTC/DNS 代理策略；未验证的 Canvas、Audio、WebGL 等能力不在 UI 中宣称支持。

7. **v0.1 是否包含实际网站打开和页面控制？**
   - 推荐：包含“打开 URL、读取标题、截图、停止”这一条最小 Worker 验证链，不包含工作流画布和批量自动化。

8. **v0.1 是否允许保存登录会话、Cookie 和代理密码？**
   - 推荐：允许本地保存必要的环境数据，但不上传团队服务；敏感字段使用操作系统安全存储，暂不做跨设备同步。

9. **环境目录默认位置如何处理？**
   - 推荐：使用系统应用数据目录，并允许在设置中修改根目录；修改前检查运行中的环境、磁盘空间和迁移失败回滚。

10. **v0.1 安装包格式是什么？**
    - 推荐：Windows NSIS 安装包 + 可选便携压缩包；macOS DMG + ZIP；均不签名，Release 提供首次启动说明和 SHA-256。

11. **v0.1 是否实现自动更新？**
    - 推荐：不实现。先通过 GitHub Release 手动下载，避免把更新服务器、回滚和签名问题提前引入。

12. **v0.1 的性能验收目标是什么？**
    - 推荐：定义冷启动时间、内核启动时间、管理界面空闲内存、单环境额外内存和连续运行稳定性目标；请确认是否接受先记录基线，v0.1 不设置硬性数值门槛。

13. **v0.1 默认界面语言是什么？**
    - 推荐：中文为默认，并保留 i18n 结构；英文可以在 v0.2 或 v0.7 再完善。

14. **v0.1 是否需要 Linux 构建？**
    - 推荐：不纳入 v0.1 的发布验收；先保留 Electron/Linux 可扩展性，避免分散 Windows/macOS 目标。

15. **是否接受 v0.1 只发布 alpha/preview？**
    - 推荐：是。v0.1.0-alpha.1 或 `preview` 通道，明确标记实验性和内核支持范围；达到稳定条件后再发布 v0.1.0。

### 内核范围的具体解释

v0.1 的第二个必验内核使用“标准 Chromium”适配器和版本化 manifest。项目不直接重新分发 Google Chrome 或 Microsoft Edge 专有二进制；后续可以探测用户本机 Chrome/Edge，或由用户配置合法的本地内核路径，但这不计入 v0.1 的下载验收。这样既能验证两套内核注册、下载、启动和能力检查，又避免把第三方专有浏览器分发义务带入首个版本。
